
> **本方案管的是写代码之前**：把需求转成机器可读的规格，并让人以渲染视图审核它。
>
> 三册关系：**1 开发前**（本册，规格构建与验收标准）→ **2 开发时**（执行、返工与账本）→ **3 发布边界与上线后**（上线前设施就位，上线后监控、诊断与需求回流）。

---

## 一、核心理念

传统开发流程用自然语言 PRD 传递需求，靠人的追问和上下文消化歧义。Agent 没有这个能力——自然语言里每一处含混，都会变成一次幻觉或一轮返工。

因此本方案的出发点只有一句话：

> **凡是要 Agent 执行的信息，必须是机器可读、可校验的规格；凡是要人审核的信息，必须是自动渲染的视图。**

由这句话推出三条原则，贯穿本方案与开发时手册：

| # | 原则 | 含义 | 违反后果 |
| :- | :--- | :--- | :--- |
| 1 | **单一事实来源** | 每类信息只在一个源文件中定义一次，其余位置只能引用 | 同一规则存在两份定义，必然漂移 |
| 2 | **单向瀑布** | 交付物严格单向依赖；下游发现上游错漏，回上游修，禁止下游打补丁 | 补丁越积越多，源头失真 |
| 3 | **源码-视图双轨** | Agent 读源文件，人看自动渲染的视图；人只改源文件，永不改视图 | 视图与源码脱节，审核失效 |

后文一切规范，都是这三条原则在具体环节的展开。

## 二、体系全景

整个体系 = **一份输入 + 六件交付物 + 三条循环**：规格循环见本册第五章，开发与返工循环见开发时手册，需求回流循环见上线后手册第四章。

分工先说死：**六件交付物的源文件默认由 Agent（Claude Code / Codex 等）生成和修改**——人主要在渲染视图上审核、用自然语言指出问题，Agent 据此改源文件；人若亲自修改，也只能改源文件，不能改派生视图。表中"视图渲染工具"只负责把源文件机械地转成人类可读视图，这一步必须由确定性工具完成、不允许 Agent 手写——否则视图本身可能与源文件不一致，人审核的就是假象；工具的配置与调用同样交给 Agent，人不碰工具链。

| # | 交付物 | 回答什么问题 | 源文件（Agent 生成+修改） | 审核视图（人看+批注） | 视图渲染工具（Agent 配置调用） |
| :- | :--- | :--- | :--- | :--- | :--- |
| ① | 语义化 HTML 原型 | 界面长什么样、有哪些交互 | `.html` | 浏览器渲染页面 | Agent 内置浏览器 |
| ② | 数据模型 | 数据是什么 | `.ts` | TypeDoc 文档站 | typedoc |
| ③ | 业务规则表 | 什么条件下发生什么 | `.yaml` | 决策表可视化 | 渲染脚本 |
| ④ | API 契约 | 前后端怎么连 | `.yaml` | Scalar 交互文档 | scalar-cli |
| ⑤ | 工程规范 | 代码怎么写才对 | `AGENTS.md` + `adr/*.md` + `SEMANTIC_GUIDE.md` | Obsidian 阅读视图 + 技术栈快照（AGENTS.md / 文档站 / README 三出口） | Obsidian（vault 指向仓库）+ 快照生成脚本 |
| ⑥ | 验收标准 | 怎么算做完了 | `.spec.ts` + `lighthouserc.json` + 截图基线 | Playwright 报告 + LHCI 报告 | playwright / @lhci/cli |

视图按产生方式分三类，对应不同的防过期手段。**下面提到的卡点完整定义见第五章**——CI 每次提交自动跑的 12 道检查，分 A、B 两组：A 组查六件套源文件**彼此**是否一致（不需要代码存在），B 组查代码是否**真的按规格执行**（需要代码存在）。

- **实时渲染型**（①的 Agent 内置浏览器、⑤的 `AGENTS.md` 正文、`SEMANTIC_GUIDE.md` 与 `adr/*.md` 本体）：你打开的**就是源文件本身**，当场渲染，不产生中间产物——天然不会过期
- **构建型**（②③④的文档站、⑤的技术栈快照）：跑一条命令**读源文件、写出另一个文件**。源文件改了而没重跑生成命令，你打开的就还是旧内容——而按原则 3 人只看视图，此时整个审核环节失效且毫无察觉。由**卡点 A1**（构建型视图随源文件变更重新生成）强制重建

  > **⑤ 是半源半派生的，别被文件名迷惑**：判断依据不是用什么打开，而是**这块内容的事实来源在不在它自己身上**。`AGENTS.md` 的正文（20 条规则、附录）与 `adr/*.md` 本体是**源**——规则和决策就定义在那里；而嵌在同一个 `AGENTS.md` 里的 **ADR 索引段**、`README` 标记块、文档站首页，全部是脚本从 `adr/` 汇总出来的**派生物**，上游改了不会自动跟着变，因此归构建型。
  >
  > 这块尤其不能过期：新增一条 ADR 却没重跑快照，`AGENTS.md` 索引段仍写着旧技术栈，而 Agent 每次对话都会自动加载它并照旧技术栈继续写代码——**ADR 索引存在的全部理由是防架构漂移，它一旦过期就自己变成了漂移的源头**。
- **执行产物**（⑥的测试报告）：它不是把 `.spec.ts` 渲染成人类可读的样子，而是**把它跑一遍看结果**——同一份用例昨天全绿今天可能全红。"报告与源文件不一致"对它不成立，因此不受 A1 约束；新鲜度由**卡点 B3**（每次提交真跑一遍测试）保证

六件交付物按依赖关系分三层，自上而下单向生成：

```
[AI 需求种子文档]（体系唯一输入，含"非 UI 能力清单"）
        │
        ▼
┌─────────────────────────────────────────────┐
│  基础层 · 定义"是什么"（优先产出，保持稳定）      │
│                                             │
│  ① HTML 原型      ② 数据模型     ③ 业务规则表  │
│  （界面与交互；规则   （TS 类型）    （规则唯一     │
│    仅以 data-rule-id               定义处）     │
│    引用③，不定义）                             │
└──────────┬──────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────┐
│  衍生层 · 定义"怎么连"（只提取，禁止独立设计）     │
│                                             │
│  ④ API 契约 ＝ ①的交互 + ②的类型               │
│              + 种子文档·非 UI 能力清单           │
└──────────┬──────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────┐
│  约束层 · 定义"怎么做才对"                      │
│                                             │
│  ⑤ 工程规范 + `adr/` 决策目录                  │
│  ⑥ 验收标准（六维度验收，反向锚定①③④）          │
└─────────────────────────────────────────────┘
```

两条全景级规则：

- **规则闭环**：业务规则只在③定义一次；①用 `data-rule-id` 引用它，④的错误码与它映射，⑥逐条覆盖它。定义、引用、验收三方由 CI 强制对齐（见第五章卡点 A3）。
- **迭代回溯**：下游发现基础层有遗漏，必须回基础层修正。不能在④里加②没有的字段，不能在⑥里硬编码③没有的规则——先改上游，再同步下游。

### 问题查找索引：先分清你在问哪类问题

遇到任何项目问题，不要顺着"六件套→代码→网上"线性翻找，**先判断问题属于哪一类**，每类只有一个权威源：

| 你在问什么 | 权威源 | 找不到意味着什么 |
| :--- | :--- | :--- |
| 应该做什么、为什么做 | 种子文档（第三章） | 需求没定义 → 走上线后手册第四章回流补 |
| 应该长什么样 / 什么数据 / 什么规则 / 什么接口 | ① ② ③ ④ | 规格有洞 → 回上游补，不在下游猜 |
| 代码怎么写、为什么这么选架构 | ⑤ + `adr/` | 决策没做 → 标「暂未决定」并去定 |
| 怎么算做完 | ⑥ | 验收缺失 → 卡点 A3 本该拦住 |
| 要做哪些事、做到哪了 | `tasks.yaml`（开发时手册 §1.3）+ 进度快照（§3.1） | 任务没拆 |
| 出过什么错、同类第几次 | `REWORK_LOG.md`（开发时手册 §5.2） | 没记 → 固化阈值失效 |
| 怎么部署、什么环境变量、怎么回滚 | ⑤附录·运行时事实 | 没记 → 排障靠猜 |
| **实际**是什么（当前现状） | 代码 + 运行时日志 / 监控 | — |
| 当时为什么这么改 | git history + PR | — |
| 外部服务怎么用 | 官方文档（联网） | 但**为什么选它**在 ADR·第三方依赖，不该去网上找 |

**最要紧的一条：代码不是权威源。**规格回答"应该是什么"，代码回答"实际是什么"。**在代码里找到了答案而规格里没有，这不叫查到了，这叫发现了漂移**——按四分类归因后回上游补规格，并记进 `REWORK_LOG.md`。把代码当兜底答案，等于默许实现反向定义规格，原则 2 就此破掉。B 组卡点存在的全部意义，就是持续检查这两类答案是否一致。

体系刻意**不**收两类信息：对外汇报文档、手工状态看板（理由见开发时手册 §5.3）。还有一类天然收不住——只在你脑子里、尚未决定的事；`adr/` 的「暂未决定」是它唯一的显性化手段。

## 三、体系输入：AI 需求种子文档

瀑布的源头不是传统 PRD，而是一份为生成而写的"种子"。两者的差别：

| 维度 | 传统 PRD（面向人） | AI 需求种子文档（面向 Agent） |
| :--- | :--- | :--- |
| 核心定位 | 沟通契约，防止理解偏差 | 生成输入源，驱动六件套产出 |
| 内容重心 | 背景、竞品、用户故事、UI 描述 | 业务目标、核心实体、关键路径、非 UI 能力、量化验收指标 |
| 表达格式 | 大段自然语言 + 静态截图 | 结构化列表 + 表格 + 伪代码/类型定义 |
| UI/UX 描述 | 文字说明（"点击后弹出提示框"） | 不写，由①HTML 原型直接承载 |
| 验收标准 | 主观描述（"体验流畅"） | 可执行指标（"LCP < 1.5s"、"③的每条规则至少 1 条用例覆盖"） |
| 生命周期 | 评审后归档，与代码脱节 | 作为生成源头，随交付物同步更新 |

种子文档固定五节，缺一不可：

1. **业务目标**——一句话产品定位 + 至多 3 条可量化成功指标
2. **核心实体**——实体名、关键字段、实体间关系（列表或伪代码）
3. **关键路径**——用户完成核心价值的最短操作序列（编号列表）
4. **非 UI 能力清单**——webhook、定时任务、第三方回调、批处理、消息通知等一切不由页面交互触发的后端能力；无则显式写"无"。此节是④的第二输入源，保证非 UI 需求在瀑布里有源头
5. **量化验收指标**——性能预算、覆盖率阈值、错误率上限

⚠️ 种子文档只回答"做什么"和"为什么"，绝不回答"怎么做"。所有实现细节由六件套承载。

## 四、六件套规范细则

每件交付物按统一模板说明：定位 → 规范要点。源文件与视图对应关系见第二章总表。

先约定各自的**更新时机**——规格不写清"何时改"，就只能靠人临场想起来，而靠想起来的规则必然漂移。**"持续更新"不是更新时机，是没有更新时机。**

| 交付物 | 何时更新 | 不因什么而动 |
| :- | :--- | :--- |
| ① HTML 原型 | 界面或交互变更时；③新增的规则有 UI 表现时 | 纯样式微调 |
| ② 数据模型 | 实体或字段增改时；④需要一个不存在的类型时（先补②再改④） | 后端存储方案变化 |
| ③ 业务规则表 | 新增规则，或既有规则的条件 / 动作变化时 | 规则的实现方式变化 |
| ④ API 契约 | ①的交互、②的类型、非 UI 能力清单三者任一变化时 | 后端内部实现重构 |
| ⑤ 工程规范 | Agent 执行偏差同类问题**第二次**出现时（阈值见开发时手册 §4.5）；架构决策变更时（新增一条 ADR，旧条只改状态不改内容）；部署、日志字段或环境变化时（改附录） | 未达到阈值的单次 Agent 执行偏差；框架漏洞——它首次即修，但修的是 CI / 生成器 / 流程，不动⑤（见开发时手册 §4.5） |
| ⑥ 验收标准 | ③新增规则时同步补用例（卡点 A3 强制）；性能预算调整时；新增角色或接口时补权限矩阵格 | 实现重构但行为不变 |

### ① 语义化 HTML 原型（基础层）

UI 与交互的单一事实来源，直接承载传统 PRD 里所有的界面描述。

- 使用 `<form>`、`<nav>`、`<main>` 等语义标签；禁止用 `div`/`span` 模拟交互控件
- 关键元素预埋 `data-testid`，供⑥绑定
- 受业务规则约束的元素标注 `data-rule-id="RULE-xxx"` 指向③；**禁止在 HTML 注释中定义业务逻辑**——注释无 schema、无校验，是幻觉重灾区
- 允许的注释仅两类：`<!-- SEMANTIC-CHECK: ... -->`（语义检查点）、`<!-- API: operationId -->`（接口锚点，仅引用④的 operationId，不描述行为）
- 审核载体为 Agent 内置浏览器。纯静态单文件可 `file://` 直接打开；一旦原型使用 ES module 或 fetch 加载 mock 数据，`file://` 会被 CORS 拦截，需由 Agent 先启动本地 preview server 再渲染——服务方式由 Agent 决定，人不介入

### ② 数据模型（基础层）

所有数据结构的单一事实来源，④的 Schema 由它自动生成。

- 每个字段必须有 JSDoc 注释：业务含义、约束、示例
- 禁止 `any`/`unknown`；数值统一最小单位（分/毫秒）；枚举用字面量联合类型
- ④的 JSON Schema 与运行时校验用的 Zod / Ajv schema **全部由本文件生成**，一律不手写——手写一份即多一个事实来源，而三份定义中必有一份先过期

### ③ 业务规则表（基础层）

业务逻辑的单一事实来源——规则在此定义一次，全体系只引用。

- 标准决策表结构：`id` + `description` + `conditions` + `actions`
- `id` 全局唯一（`RULE-` 前缀），是①和⑥引用规则的唯一句柄
- 提供 JSON Schema，CI 强制校验结构；禁止在 YAML 中写大段自然语言注释

### ④ API 契约（衍生层）

前后端连接方式的完整描述，只从上游提取，不独立设计。

- 输入源限定三处：①的交互、②的类型、种子文档·非 UI 能力清单；三处之外的接口不得出现
- Schema 与②同源：`ts-json-schema-generator` 自动生成 JSON Schema 并 `$ref` 引用，禁止手写重复定义
- 每个接口必须有语义化 `operationId`；错误响应结构化（`code` + `message`），`code` 与③的规则 id 可映射

### ⑤ 工程规范（约束层）

Agent 写代码时的硬性约束，以 `AGENTS.md` 形式常驻上下文。

- 内容：目录结构、命名规范、禁止事项（如禁止 `any`）、日志格式；**单个文件规则不超过 20 条**，避免挤占上下文窗口
- 超过 20 条时**分层而非扩容**：根目录 `AGENTS.md` 只留全局约束，子目录各自放一份局部规范，Agent 按当前工作路径按需加载。扩容会让每次对话都拖着用不上的规则，分层不会
- 日志必须结构化并服务于可定位（见开发时手册 §4.1、上线后手册第二章）：Agent 排障没有"我记得当时"，只有日志里写着的；具体字段 schema 统一放在⑤附录，不在正文和业务代码各写一份
- **附录·运行时事实**：部署命令、环境变量**名**清单（只记名不记值，密钥永不进仓库）、回滚步骤、健康检查地址、CI 进度快照的生成 / 读取命令，以及线上日志六个键的字段 schema 与注入方式。这些不是决策而是操作事实，Agent 排障、调度和发布时必须能查到；不计入 20 条规则上限
- 审核载体为 Obsidian，且 **vault 必须直接指向仓库目录**（或仓库内 docs 子目录）：`AGENTS.md` 本体留在仓库根，供 Agent 自动加载；严禁把它复制进独立 vault——两份副本即违反原则 1
- 正文限标准 Markdown（CommonMark / GFM）。Obsidian 私有语法（`[[wikilink]]`、dataview、自定义 callout）不得进入源文件，否则 Agent 读到的是渲染器方言而非规范本身

#### ⑤-b 技术方案 ADR（`adr/*.md`）

架构决策的唯一承载处——**进入开发阶段后不再写任何散文式"技术方案文档"**：系统结构已由①②④隐含承载，数据库设计已在②，接口设计已在④，需要单独记的只剩"为什么这么选"。

- **一决策一文件**，编号只增不复用。编号取自**引入它的 PR 号 + 该 PR 内序号**（序号从 1 起，只有一条时也写 1）：`adr/ADR-142-1-订单状态机.md`。PR 号在仓库内单调递增且永不复用，因此多设备并行时零协调、不可能撞号；起草阶段尚无 PR 号，先叫 `adr/draft-<slug>.md`，开 PR 后重命名
- **固定五段**，每段一到三行；其中「边界」必须是可监控或可人工判定的重新评估条件：

  ```markdown
  # ADR-142-1：订单状态机采用数据库枚举而非独立服务
  ## 状态：已采纳          <!-- 已采纳 / 已取代（→ADR-207-1） / 暂未决定 -->
  ## 背景：订单量 < 1 万/天，无需分布式状态机
  ## 决策：orders 表使用 status ENUM 字段
  ## 后果：简单高效；量级上来后需重构为独立服务
  ## 边界：订单量连续 7 天达到或超过 1 万/天时重新评估
  ```

- **状态字段是机器可读的**：被推翻的 ADR **不删除、不改内容**，只把状态改为「已取代」并指向新编号。历史决策留着，才回答得了"当时为什么这么定"
- **七类必覆盖**，每类至少一条 ADR；确实还没定的写「状态：暂未决定」，**不许留白**——留白 Agent 会自己发明，写明暂未决定它才会来问：

  | 类别 | 举例 |
  | :--- | :--- |
  | 技术栈 | 框架、运行时、包管理器、数据库 |
  | 分层与目录 | 按功能还是按类型分、跨层调用规则 |
  | 数据流 | 状态管理方案、服务端 / 客户端边界 |
  | 鉴权 | 会话机制、权限模型 |
  | 错误处理 | 错误码体系、边界降级策略 |
  | 部署形态 | 托管平台、构建产物形式、环境划分 |
  | 第三方依赖 | 引入了什么、为什么不自己实现 |

- **索引由 CI 生成，不手写**：只含决策结论，不含背景与后果。原因是 `AGENTS.md` 会自动进 Agent 上下文而 `adr/` 目录不会——**Agent 读不到的 ADR 拦不住架构漂移**；索引让结论常驻上下文，需要理由时 Agent 再去读全文。索引是生成视图不是手抄副本，因此不违反原则 1

##### 索引形态：按七类归组的"当前技术栈快照"

索引不是 ADR 的目录，而是**当前技术栈的快照**——它要在一屏内回答"这个项目现在用什么、怎么分层、部署在哪"，而不是让人读完 30 条 ADR 自己组装。因此生成规则有三条硬性要求：

1. **当前决策只取 `状态：已采纳`**——`已取代` 的条目不进快照（仍留在 `adr/` 可追溯）；若某类别没有已采纳项但存在「暂未决定」项，则按第 3 条输出待定状态。ADR 目录只增不减，不过滤状态的索引迟早会让人读到已废弃的结论，而外部读者最没有能力识别这一点
2. **按七类归组**，不按编号排列——编号顺序反映决策发生的时间，与"当前是什么"无关
3. **`暂未决定` 的类别照常列出**并标注状态，不静默省略——缺项被省掉就看不出"这里还没定"，读者会默认它已经定了

生成结果形如：

| 类别 | 当前决策 | 依据 |
| :--- | :--- | :--- |
| 技术栈 | Next.js 15 + PostgreSQL + pnpm | ADR-12-1, ADR-31-2 |
| 分层与目录 | 按功能域分包，禁止跨域直接 import | ADR-12-2 |
| 鉴权 | *暂未决定* | ADR-58-1（待定） |

**三个渲染出口，同一份生成内容**：

| 出口 | 给谁 | 为什么需要 |
| :--- | :--- | :--- |
| `AGENTS.md` 索引段 | Agent | 自动进上下文，防架构漂移 |
| 文档站首页（与 TypeDoc / Scalar 同批发布） | 项目外的人 | 零安装、给个 URL 就能看，不必 clone 仓库或装 Obsidian |
| `README.md` 标记块（`<!-- ADR-SNAPSHOT:BEGIN / END -->`，CI 覆写块内内容） | 打开仓库的人 | 第一眼可见，不必知道 `adr/` 目录的存在 |

三处内容完全相同且全部由 CI 从 `adr/*.md` 生成，因此不构成副本——**手写其中任何一处即违反原则 1**。这也是本方案唯一认可的"技术栈说明"形态：单独写一份给人读的技术栈文档，等于把已被拒绝的散文式技术方案换个名字请回来。

#### ⑤-c 不要另建"上下文注入配置"

常见的一个诱惑是再加一个 `.agent-context.json` 之类的文件，把安全要求、性能基线、禁止模式打包成 JSON"自动注入"。**不要建**——它的三类内容各自都已有更好的归宿，另建只会制造第二事实来源：

| 想放进去的东西 | 为什么不放 | 正确归宿 |
| :--- | :--- | :--- |
| 性能基线（LCP 等） | 与 `lighthouserc.json` 重复，两处必有一处过期 | ⑥的性能预算文件，CI 真的会拦 |
| 禁止模式（`console.log`、`any`、硬编码密钥） | 写成 JSON 清单只有劝告效力 | ESLint 规则 + gitleaks，红灯可阻断 |
| 安全要求（"所有 API 必须校验 JWT"） | JSON 数组里的自然语言不是机器可读——**JSON 语法 ≠ 机器可读语义**，无 schema、无校验，与"在 HTML 注释里写业务逻辑"是同一种错误 | 能测的写成⑥的用例；只能约束的写进⑤正文 20 条 |

"自动注入上下文"本来就是 `AGENTS.md` 的职责，不需要第二个文件代劳。

#### ⑤-d 语义分册 `SEMANTIC_GUIDE.md`

第五章防幻觉机制引用的根目录 `SEMANTIC_GUIDE.md`（语义对照表）是⑤的组成部分，与 `adr/` 并列，不是第七件交付物：

- **定位**：源文件、实时渲染型——Markdown 本体即源，不受卡点 A1 约束；审核视图同⑤为 Obsidian
- **内容分流**（与⑤-c 同一原则）：axe 能测的语义规则不收——那是⑥/B4 的职责，重复收录即制造第二事实来源；只收机器测不了、只能约束的语义约定（如控件的语义选型）
- **上限**：不计入根 `AGENTS.md` 的 20 条，但自身同样适用 20 条上限与分层原则
- **更新时机**：同⑤阈值——语义类的同类 Agent 执行偏差第二次出现才增条（开发时手册 §4.5）
- **加载时机**：仅 UI 任务（修改①、或 `writeSet` 触及前端目录）下发时注入，非 UI 任务不带——与⑤的按需加载一致

### ⑥ 验收标准（约束层）

"做完"的唯一判据。核心分工：**机器验证正确性，人验证合理性**——能写成断言的一律不许靠人看；人的注意力只留给机器判不了的那类问题：这个业务逻辑合不合理、这个交互符不符合直觉。

六个维度，各有独立载体，互不混装：

| 维度 | 载体 | 验什么 |
| :--- | :--- | :--- |
| 功能 | `.spec.ts` | 关键路径跑通、规则被覆盖 |
| 契约一致性 | `tsc` + 契约测试 + 运行时校验 | 实现是否真的遵守②④ |
| 无障碍 | axe-core（并入 spec 同批跑） | 语义标签、ARIA 是否合规 |
| 安全 | 权限矩阵用例 + 依赖/密钥扫描 | 越权、已知漏洞、密钥泄漏 |
| 性能 | `lighthouserc.json` | LCP / CLS 等预算 |
| 视觉 | 截图基线 | 非预期的 UI 改动 |

**功能**：绑定①的 `data-testid` 与④的契约；每条用例注释标明覆盖的 `RULE-xxx`；中文注释说明验收意图。

**创建时机**：⑥属于开发前规格，进入开发时手册之前就必须生成；A3 只静态检查规则引用与用例定义是否存在，不要求此时已有实现或用例通过。开发阶段的“测试步”负责在当前 `Task-ID` 下首次执行这些预写用例并确认先红；若线上故障暴露了新边界，再先补充一条能复现故障的用例，然后进入实现。

**契约一致性**——这是「规格自洽」与「实现符合规格」之间的桥，也是本方案此前最大的漏洞：六件套彼此对得上，不代表代码按它执行了。三件事：

- `tsc --noEmit` 进 CI，类型不匹配直接阻断
- **契约测试**：工具读④的 OpenAPI 自动向真实服务发请求，验证响应结构、状态码、字段类型与契约一致。据我所知 Schemathesis 维护活跃、Dredd 已长期低维护，优先前者
- **运行时校验**：Zod / Ajv 校验进出数据，但 **schema 必须从②生成**（`ts-to-zod` 一类工具）。手写 Zod 即制造第三份数据定义（②、④的 JSON Schema、Zod），违反原则 1
- **覆盖口径写死**：④中每个 `operationId` 的**每个已声明状态码**至少被契约测试触达一次。"覆盖率 100%"不写明分母就不是可执行指标，与本方案拒绝"体验流畅"是同一个理由

**无障碍**：`@axe-core/playwright` 并入功能测试同批执行。①规定了语义标签与 `aria-label`，但此前没有任何东西强制它——axe 就是那道缺失的闸门。

**安全**（轻量口径，不引入红队框架）：

- **权限矩阵用例**：④的每个 `operationId` × 每个角色 → 期望状态码，逐格写成 spec 用例
- `npm audit`（或等价）+ gitleaks 密钥扫描进 CI
- 不引入红队框架：本方案面向产品自身不含 AI 能力的场景，安全验收止于上述三项

**性能**：LCP / CLS 等写入预算文件，由 Lighthouse CI 在受控环境独立执行——性能断言不进功能测试，避免环境波动造成 flaky 红灯。

**视觉**：截图基线对比的是**上一次构建**，用途是发现非预期的 UI 改动；Playwright 自带 `toHaveScreenshot()` 即可，无需付费 SaaS。**基线是有意改动时才更新的**——UI 确实要改，就在同一个 PR 里连带更新基线文件（`--update-snapshots`）并在 PR 描述中说明；红了就顺手更新基线，等于把这道闸门关掉。**不要拿实现去和①原型做像素对比**——原型是静态 mock，实现有真实数据、字体加载、loading 态，像素比必然噪声爆炸，最终结果是所有人闭眼点 approve。实现与①的一致性由**结构对比**保证（语义标签、`data-testid` 完整性），即第五章的原型自检机制。

**证据可追溯**：每份验收报告必须携带与线上日志同源的六个键：`commit`、`taskId`、`ruleId`、`operationId`、`dataTestId`、`adr`；不适用的条件键显式为 `null`，不得省略。孤立的截图或分数不构成证据——出问题时它回答不了"这条规则当时到底验过没有"。

## 五、规格循环

规格写好后，人、CI、Agent 按同一条循环协作：

```
[人] 审核渲染视图（Agent 浏览器 / TypeDoc / 决策表 / Scalar / Obsidian / 测试报告 / LHCI 报告）
      │ 用自然语言指出问题，不动手改                     ↑
      ▼                                              │ 确定性工具重新渲染
[Agent] 修改对应源文件                                 │
      │ （人若亲自动手，也只允许改源文件）               │
      ▼                                              │
[CI] 重新生成全部视图 + 跑卡点校验 ─────────────────────┘
      │ 全绿
      ▼
[Agent] 携规格进入开发阶段 → 见《开发时执行与返工手册》
```

### CI 卡点（提交即触发，任一红灯即阻断）

闸门的分工原则：**机器能判的一律交给机器，人只出现在机器判不了的地方。**下列各项全是确定性检查，人不复核。

卡点分两组，区别关系重大：

**两组卡点的生效时机不同，这一点第一天就会遇到**：A 组只依赖源文件，六件套一写完就该全绿；**B 组需要实现存在，只对当前 PR / commit 通过 `Task-ID: Txxx` 明确关联、且已首次执行验收用例的任务激活**。未关联任务不运行 B 组，不产生“正常红灯”。激活后按任务能力裁剪：B1、B3、B6 必跑；B2、B5 仅 L2 接口任务运行；B4、B8 仅 UI 任务运行；B7 仅影响可部署页面或性能路径的任务运行。CI 必须输出本次启用与跳过的卡点及理由，不能静默跳过。

**A 组·规格自洽**——六件套源文件之间是否一致

| # | 卡点 | 拦截什么 |
| :- | :--- | :--- |
| A1 | 构建型视图（②③④的文档站 + ⑤的技术栈快照三出口）随源文件变更重新生成 | 视图过期（①与⑤正文为实时渲染；⑥的测试报告由 B 组产出，不在此列） |
| A2 | ③的 JSON Schema 校验 + 规则冲突检测 | 非法 / 矛盾规则 |
| A3 | 规则引用完整性 lint：①的每个 `data-rule-id` 存在于③；③的每条规则被⑥至少一条用例覆盖 | 悬空引用、无验收的规则 |
| A4 | ④与②的 Schema 同源比对 | 契约与类型漂移 |

**B 组·实现符合规格**——代码是否真的按规格执行

| # | 卡点 | 拦截什么 |
| :- | :--- | :--- |
| B1 | `tsc --noEmit` | 类型违规 |
| B2 | 契约测试对真实服务跑④（每个 operationId × 每个已声明状态码） | 实现偏离接口契约 |
| B3 | ⑥功能测试 + 覆盖率阈值 | 逻辑错误、覆盖缺口 |
| B4 | axe-core 无障碍扫描 | 语义标签 / ARIA 违规 |
| B5 | 权限矩阵用例（operationId × 角色 → 期望状态码） | 越权 |
| B6 | 依赖漏洞扫描 + gitleaks 密钥扫描 | 已知漏洞、密钥泄漏 |
| B7 | Lighthouse CI 性能预算 | 性能回退 |
| B8 | 视觉回归（对比上一次构建） | 非预期的 UI 改动 |

**为什么必须分组**：A 组全绿只证明六件套彼此不矛盾，**完全不证明代码按它执行了**——规格与实现可以各自漂移而 A 组始终绿灯。B 组就是为堵这个洞而存在的；只上 A 组的项目，等于有一套自洽但无人遵守的规格。

**L1 阶段哪些卡点不启用**：A2、A3、A4、B2、B5 依赖③或④，四件套阶段一律跳过，升 L2 时随③④一并启用。此时 `tasks.yaml` 的 `ruleRefs`、`operationRefs` 一律填空数组 `[]`（字段仍必填，保持结构稳定），"每条规则被任务覆盖"那道卡点同样不启用——③引入之后再回填。

### Agent 执行规范

**局部修改指令四要素**——向 Agent 下发修改任务时，语义、无障碍、数据与规则绑定、锚点四项缺一不可：

> "修改 prototype.html 中的【订单提交按钮】，要求：
> 1. **语义化**：必须使用 `<button type="submit">`，包裹在 `<form>` 内；禁止 div/span 模拟。
> 2. **无障碍**：添加 `aria-label="提交订单"`；禁用时加 `disabled` 属性而非仅 CSS 置灰。
> 3. **数据与规则绑定**：按钮文本从 `orderData.submitText` 读取；点击绑定 `handleSubmit`，参数符合 types.ts 的 `SubmitOrderPayload`；库存禁用逻辑标注 `data-rule-id="RULE-STOCK-001"`（规则定义在 rules.yaml，不在此处描述）。
> 4. **锚点**：接口锚点注释更新为 `<!-- API: submitOrderV2 -->`。"

**防幻觉机制**：

| 机制 | 触发时机 (W) | 动作 (A) | 结果 (R) |
| :--- | :--- | :--- | :--- |
| 语义检查点 | Agent 修改 HTML 时 | 遵守 `SEMANTIC-CHECK` 注释标注的标签规范 | 语义标签不被降级 |
| 原型自检 | Agent 改完①、交人审核之前 | 用内置浏览器打开原型，读取可访问性树，核对语义标签、`aria-*` 与 `data-testid` 是否与规范一致 | 结构错误在到达人之前由 Agent 自己发现，人只审业务合理性 |
| 语义对照表 | UI 任务下发时 | 将根目录 `SEMANTIC_GUIDE.md`（⑤-d 语义分册）作为上下文传入 | 规范不依赖 Agent 记忆 |
| 规则引用 lint | 每次提交 | CI 跑卡点 A3 | 定义/引用/验收三方一致 |
| 测试驱动语义 | Agent 改完后 | 运行语义相关测试用例 | 规范转化为可验证代码 |

**变更影响申报**：Agent 修改任一基础层文件前，必须先列出受影响的下游清单（④⑤⑥中哪些需同步更新），确认后一并修改；禁止只改上游不动下游。

## 六、分级落地

六件套是完整形态，不是起步门槛。按项目复杂度分两级采用：

| 级别 | 交付物 | 适用 |
| :--- | :--- | :--- |
| **L1 四件套** | ① ② ⑤ ⑥ | MVP、单人、后端逻辑简单 |
| **L2 六件套** | L1 + ③ ④ | 后端复杂度出现后 |

L1 阶段业务规则的临时归宿：写入⑥的测试用例 + ②的类型约束（字面量联合、JSDoc 约束说明），**不写入 HTML 注释**。

**L1 → L2 升级触发条件**（满足任一即升级，禁止在 L1 硬撑）：

| 触发时机 (W) | 动作 (A) | 结果 (R) |
| :--- | :--- | :--- |
| 规则条数 > 10，或同一规则被 ≥2 个页面复用 | 引入③，回填既有规则 | 规则单一事实来源建立 |
| 前后端分离开发，或出现第三方调用方 | 引入④ | 接口契约化，可 Mock 可校验 |
| 出现非 UI 触发的后端能力（webhook / 定时任务 / 批处理） | 引入④ + 种子文档补非 UI 能力清单 | 非 UI 需求有源头 |

**落地纪律**：

1. **初始化**：渲染与校验流水线由 Agent 配置并调用，人不碰工具链。L1 需 Agent 内置浏览器（①）+ TypeDoc（②）+ Obsidian 打开仓库为 vault（⑤）+ Playwright / axe-core / LHCI / `tsc` / gitleaks（⑥）；L2 再加 Scalar、决策表渲染、契约测试与权限矩阵用例。以 CI 卡点全绿为初始化完成判据，不以时长为判据；预期投入按一天到一天半规划——比只上 A 组卡点时多出的部分，全部花在 B 组，而 B 组正是唯一能证明代码遵守规格的一组。
2. **审核会议**：投屏渲染后的文档站 / 报告，不投 IDE 里的源码。文档站首页放两张 CI 生成的快照——**技术栈快照**（⑤-b）与**进度快照**（开发时手册 §3.1）。项目外的人问"用什么技术栈""做到哪了"，给同一个 URL 即可，不必 clone 仓库。
3. **修改纪律**：默认由 Agent 修改源文件，人只负责在视图上发现问题、用批注或指令描述问题；人若亲自动手，也只允许编辑源文件，禁止直接改生成的文档 / 报告。
4. **非技术协作**：业务方在 Notion / 飞书查看同步的 Markdown 视图并批注，开发根据批注回溯修改源文件；禁止业务方直接编辑源文件。

## 七、适用边界

| 场景 | 适用性 | 说明 |
| :--- | :--- | :--- |
| Web 应用、SaaS、工具类产品、MVP 验证 | ✅ | 本方案主场 |
| 单人 / 小团队 + Agent 协作 | ✅ | 从 L1 起步 |
| 强合规审计项目 | ❌ | 需保留人类可读决策记录 |
| 多人 / 多 Agent 大规模协作 | ❌ | 需增加模块间接口协议 |
| 遗留系统深度集成 | ❌ | 需增加现有系统架构图 |

---

**核心价值**：需求从"自然语言描述"变为"机器可读规格"——规则有 schema、引用有 lint、契约与类型同源；人类始终面对渲染视图而非源码；流程开销随分级采用与团队规模匹配。Agent 由此从"需要反复纠正的实习生"变为"精准执行的重构工程师"。
