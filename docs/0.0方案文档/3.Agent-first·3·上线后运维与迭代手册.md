
> **本手册管的是发布边界与上线之后**：§1 在首次上线前完成设施就位；§2–§4 管上线后问题怎么定位、诊断、修复，以及真实反馈如何合法地回到需求源头或 ADR。
>
> 三册关系：**1 开发前**（规格构建与验收标准）→ **2 开发时**（执行、返工与账本）→ **3 发布边界与上线后**（本册，上线前设施就位，上线后监控、诊断与需求回流）。

---

## 〇、适用范围与本册结构

本册面向**产品自身不含 AI 能力**的场景——Agent 是开发者，不是交付物。产品若日后引入模型调用，需另行补充相应的运行时监控与评估，不在本册范围。

**本册的四个动作**：**就位**（§1）→ **定位**（§2）→ **诊断**（§3）→ **回流**（§4）。它们严格顺序依赖——没有§1 的设施，§2 拿不到数据；没有§2 的标识，§3 只能猜；没有§3 的归因，§4 回流的是错的需求。

---

## 一、就位：上线前必须建好的东西

后面三章全部依赖这一章，所以它排在最前。设施按需分级，不一次建齐：

| 层 | 何时建 | 组件 |
| :--- | :--- | :--- |
| **起步** | **首次上线前，硬性** | 错误上报（Sentry 一类）+ 结构化日志（带§2 的六个键）+ 可用性告警 + Commit / Task 构建映射 |
| **回流就绪** | 开始依据线上反馈做迭代前 | 最小反馈入口 + 种子文档关键路径逐步埋点；否则第四章对应信号显式标“未采集” |
| **增强** | 用户量、事故频次或 ADR 边界监控需求上来后 | 指标看板、ADR 边界告警、feature flag 灰度发布 |

起步层没有商量余地：**没有携带六个键的结构化日志和 Commit / Task 构建映射，第二章整章失效**，后面的诊断与回流也就无从谈起。关键路径完成率不凭空存在；未建设“回流就绪”层时，不得在报告里输出该指标或据此下结论。

灰度发布对单人 MVP 通常是过度设计——它解决的是"改动影响面大且回滚慢"的问题，而本方案的读者往往可以直接回滚重发。等到回滚一次的代价开始变得可感，再建。

## 二、定位：六个键

开发时手册 §4.1 要求出错时能一眼看出是哪条 `RULE-xxx`、哪个 `operationId`、哪个 `data-testid`。**上线后这条要求不降级，再增加 `commit`、`taskId`、`adr`，统一成六个键。**

线上每一条错误上报与结构化日志，必须携带以下六个键；版本 / 任务键按下述规则注入，条件型键不适用时显式填 `null`，不得删键：

| 字段 | 来源 | 用途 |
| :--- | :--- | :--- |
| `commit` | 构建时注入 | 定位到确切代码版本 |
| `taskId` | PR / commit 的 `Task-ID` + 构建映射 | 定位到最近引入或修改该应用代码路径的功能任务；基础设施通用错误可为 `null` |
| `ruleId` | ③（若涉业务规则） | 定位到具体规则，而非"订单模块异常" |
| `operationId` | ④（若涉接口） | 定位到具体接口 |
| `dataTestId` | ①（若涉 UI 元素） | 定位到具体交互元素并反查⑥用例 |
| `adr` | `adr/*.md`（若涉架构决策） | 判断是否触及某条决策的边界条件 |

**这六个键是整套体系上线后仍然成立的关键。**构建流水线从已合并 PR / commit 的 `Task-ID` 生成“源文件路径 → 最近任务”映射，错误追踪借助 source map 取最上层应用代码路径并回填 `taskId`；无法映射的基础设施错误填 `null` 并在诊断报告说明原因。没有这条链，线上指标只能告诉你"订单模块错误率上升"；有了它，能直接指到 `RULE-COUPON-003`、`createOrder` 或具体 `dataTestId`，顺着找到⑥里对应的验收用例，问出那句最要紧的话：**这条规则当时到底验过没有？**

六键的名称、类型、可空条件和注入方式在⑤的附录中固定，不由各处自行发挥。

## 三、诊断：从问题到 PR

**禁止让人去翻日志猜原因。** 有了第二章的标识，诊断就是一条固定链路，每一步的产出都是下一步的输入：

```
捕获 → 关联 → 根因 → 人工确认 → 契约 → 测试 → 实现 → PR/CI 闸门 → 人工合并
```

| 步 | 做什么 | 纪律 |
| :- | :--- | :--- |
| **捕获** | 告警 / 用户反馈 / 错误上报自动建 issue | issue 自动带上第二章的六个键；无法映射项保留 `null` 与原因 |
| **关联** | 拉取该请求的结构化日志、错误堆栈，以及它命中的规则、接口、UI 元素与 ADR | 用常规错误追踪即可，按第二章六键检索，不需要额外的追踪体系 |
| **根因** | Agent 读日志 + 堆栈 + 对应规格，输出结构化诊断报告 | 归因**必须用开发时手册 §4.2 的四分类**，不另起一套故障词表 |
| **人工确认** | 人只审诊断报告是否成立，不重新排查 | 报告里的原始报错必须是原文，不许安抚性转述 |
| **契约 → 测试 → 实现** | 走开发时手册 §2 的前三步 | 若现有⑥不能复现故障，先补一条复现用例并确认先红，再写实现 |
| **PR / CI 闸门** | 开 PR 后由 CI 跑 A 组 + 当前 `Task-ID` 适用的 B 组 | 与开发期同一套标准，不因"线上紧急"降级；CI 输出启用 / 跳过项及理由 |
| **人工合并** | 人审核诊断、改动和真实闸门输出后合并 | Agent 不直接改生产，也不自动合并 |

### 3.1 归因沿用同一张表

线上故障不需要新的归因体系，开发时手册 §4.2 的四类全部装得下：

| 归因 | 线上表现 | 处置 |
| :--- | :--- | :--- |
| Agent 幻觉 | 实现偏离明确规格，包括编造字段 / 接口，也包括普通编码错误、漏分支和边界处理错误 | 修实现并记录；同类第二次才补⑤禁止项，不动正确的业务规格 |
| 框架漏洞 | CI、生成器、schema、任务推导或流程机制自身缺失 / 错配 | 首次确认即修机制或加卡点（**唯一**不等待第二次即可新增卡点的归因） |
| 业务理解偏差 | 规格本身就写错了，或需求本身变了 | 需求变了走第四章回流；规格写错了回基础层改 |
| 外部环境失败 | 第三方服务、网络、配额、版本、平台 | 记录现场；若要新增降级行为，回③⑥、ADR 或⑤附录定义，事故噪音本身不固化成通用编码规则 |

维持一套归因词表的意义在于：`REWORK_LOG.md` 的「主归因」列能把开发期问题和线上问题放在一起计数。主归因必须四选一；“为什么没被闸门拦住”另记在「逃逸原因」列，不把普通实现错误和框架机制错误混为一类。**同类 Agent 执行偏差在开发期出现过一次、上线后又出现一次，就是第二次**，触发⑤固化阈值；确认是框架漏洞则首次即修。

每条线上故障都要在 `REWORK_LOG.md` 里追加一行，与开发期返工同表同格式。

### 3.2 三条红线

- **禁止 Agent 直接修改生产环境。**所有修复走 PR + CI，人工审批。Agent 可以做的是诊断、生成修复、跑通验证并开 PR；**按下合并的始终是人**。否则"越修越坏"没有任何东西能拦住。常见的"自愈飞轮"说法——监控发现问题 → 自动诊断 → 自动修复 → 自动上线、无需人工干预——与这条红线直接冲突，**以红线为准**。
- **原始证据归档。**故障解决后，错误堆栈原文、相关日志片段随 issue 留存，不因"已修复"而清理。
- **Agent 执行偏差同类第二次固化，框架漏洞首次即修**，与开发时手册 §4.5 一致。不要另定"第三次"之类的阈值——两个数并存，执行时就不知道该听谁的。

## 四、回流：从线上数据到种子文档

这是本手册最重要的一章，它补上了前两册的一个结构性缺口。

前两册的瀑布是严格单向的：种子文档 → 六件套 → 代码。迭代回溯原则只处理"下游发现上游写错了"，**不处理"线上发现需求本身不对"**——而后者恰恰是上线之后最常发生的事。没有合法入口，这类需求就会绕过种子文档直接改六件套，单向瀑布就此破掉。

### 4.1 两类信号的唯一合法路径

```
[线上信号]
    │
    ├─ 需求信号：负反馈 / 错误路径 / 关键路径完成率
    │      ▼
    │  [更新 AI 需求种子文档] ← 需求变化必经，不许跳过
    │      ▼
    │  [影响分析后按 ①②③ → ④ → ⑤⑥ 更新受影响项]
    │
    └─ 架构信号：ADR 边界触发
           ▼
       [重评并新增 ADR；旧 ADR 仅改状态]
           ▼
       [按影响分析更新受影响的规格 / 实现]
              │
              ▼
      [A 组全量 + 各受影响 Task-ID 的适用 B 组回归]
              │
              ▼
      [发布 + 观察同一批指标是否改善]
```

**硬性规定：线上发现的需求问题，必须先改种子文档。**直接改六件套或代码，会让种子文档与真实需求脱节。纯架构边界触发不改种子——种子只回答“做什么 / 为什么”，此时应新增 ADR，并把旧 ADR 状态改为“已取代”；只有边界变化同时改变业务目标、核心实体、关键路径、非 UI 能力或量化指标时，才先改种子。两条路径都只更新影响分析命中的源文件，但都做全量 A 组与受影响任务的适用 B 组回归。

### 4.2 四类线上信号

| 信号 | 怎么采 | 说明什么 |
| :--- | :--- | :--- |
| 用户负反馈聚类 | 反馈入口自动附带当前页面 / 操作的六键上下文，工单按 `ruleId` / `operationId` 归组；无法映射项保留 `null` | 哪条规则的设计本身让用户难受 |
| 高频错误路径 | 错误上报按第二章六键聚合，并先排除已归因为「Agent 幻觉」的事件 | 可能是规则或接口设计缺陷；不能仅凭频次把实现 bug 判成需求问题 |
| 关键路径完成率 | 前端埋点，对应种子文档·关键路径的每一步 | 用户在哪一步走不下去 |
| **ADR 边界触发** | ADR 固定第五段「边界」写明的条件被突破时告警 | 走 ADR 重评路径；不自动改种子文档 |

最后一条值得特别说明：⑤的每条 ADR 都有固定第五段「边界」，例如“订单量连续 7 天达到或超过 1 万/天”。增强层把可观测边界接进监控；暂时无法自动采集的边界必须写明人工复核时机，不能假装已监控。边界命中只触发重评，不代表原决策自动失效。

### 4.3 优先级排序：不要用公式

常见做法是合成一个分数，例如 `(影响用户数 × 严重度) / (修复成本 × 风险系数)`。**不要这么做**，两个理由：

- 分母里的"修复成本"通常由 Agent 或人估算，而工作量估算出了名的不准。用不可靠的数做分母，整个排序就是伪精确
- 权重（严重度 3/2/1、风险 3/2/1）是拍脑袋定的，但公式的外形会让它看起来客观，从而**压制质疑**。给主观判断套一层数学外衣，比诚实的主观排序更危险

替代做法——只用可直接测量的量，且不合成单一分数：

1. **命中支付或权限的，一律最高优**（二值判断，不参与计算）
2. 其余按 `触发频次 × 受影响用户占比` 降序，两个量都直接从监控读出
3. **修复成本由人在排序结果上做最终裁量**，作为独立输入，不塞进分母

保留人的裁量是刻意的：它是主观的，那就让它明着主观，而不是伪装成公式的一部分。这与开发时手册 §3.2 拒绝工时估算是同一条思路——**能测的就测，测不了的就明说测不了，不要用估算填空。**

---

**收束**：四个动作合起来是一句话——**先把设施就位，让每条线上问题带着标识出现，顺着标识诊断归因，再让需求结论回到种子、架构结论回到 ADR。**

三册至此闭环：开发前把需求变成机器可读的规格，开发时把规格变成可验证的代码，上线后把真实世界的反馈变回规格的输入。

闭环成立的前提只有一个：**每一条应用层线上问题都能顺着六个键回到它出生的规格或决策；不适用项明确为 `null` 并可解释**。这个标识链断在哪里，闭环就在哪里变成开环。
