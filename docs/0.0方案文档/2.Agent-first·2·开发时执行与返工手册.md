## 一、拆：任务边界与清单

任务怎么拆，代码就怎么分。这一步决定的不是开发效率，而是**将来返工的成本**——边界含糊，改一处牵动全局；边界清晰，返工才可能是局部的。

### 1.1 边界判据

一个任务的边界算清楚了，标志是这三组引用都能显式列出：

1. 它覆盖种子文档·关键路径的**哪一段**
2. 它读取**哪些 `RULE-xxx`**（L1 可为空数组）
3. 它调用**哪些 `operationId`**（L1 或纯 UI 任务可为空数组）

**三个字段不可省；按级别本应有引用却列不出来就别开工**——列不全不代表任务拆得不好，更可能说明规格本身有洞。此时回规格循环补，而不是让 Agent 边写边猜。

**边界重叠看写集，不看引用集**：两个任务读取同一条 `RULE-xxx` 或调用同一个 `operationId` 很正常，契约的价值正是让多个实现可以共享同一规格。只有 `writeSet` 中的文件或目录发生包含 / 相交，才说明它们在改同一块东西；此时要么合并，要么把公共写入拆成第三个任务先做。

这条判据还有第二个用途——它同时就是"**两个任务能否同时开工**"的判据，下一节展开。

### 1.2 拆的时候就要为并行留出空间

若后续要多设备并行（见《多设备协同并行多功能开发SOP》），**并行度在拆任务这一步就被决定了**——派工时才发现拆不开，已经晚了。

**一、垂直切，不要水平切**

| 切法 | 一个任务是什么 | 并行后果 |
| :--- | :--- | :--- |
| **水平切**（按技术层） | "把所有实体的 model 写完"、"把所有接口实现一遍" | 每个任务都碰所有文件，任务间必然冲突；且后一层必须等前一层，全串行 |
| **垂直切**（按功能域） | "下单流程步骤 3：它的规则 + 它的接口 + 它的界面" | 各任务的文件占用天然不重叠，可同时开工 |

§1.1 的三条判据本身就在逼你垂直切：`pathSegment` 要的是**关键路径的一段**，不是某一层的全部；`ruleRefs`、`operationRefs` 与 `specRefs` 跟着这一段走。**这些字段无法落到同一段关键路径的任务，多半是水平切出来的。**

**二、拆完立刻算并行宽度**

按 `dependsOn` 把任务分层——第 0 层是无依赖的，第 n 层的依赖只落在前 n−1 层。每层的任务数就是那一轮的并行上限。

- 最大层宽 = 1 → 拆成了一条链，设备再多也用不上，回去重拆
- 最大层宽 ≥ 你的可用会话数 → 够用

**三、降链深的两个手法**

- **前后端不必串行**。④的契约已经定死了接口形状，前端任务对着 mock 就能做，**不需要 `dependsOn` 后端任务**。契约先行最大的红利就在这里——如果你的任务图里前端普遍依赖后端，说明这个红利没吃到。
- **公共部分先抽出来，做成星形而非链形**。三个任务都要用同一段逻辑时，抽成 T000 让三者各自依赖它，而不是排成 T001 → T002 → T003。

**四、共享文件的改动集中做**

`tasks.yaml`、`AGENTS.md`、⑤的附录这类全局文件，若每个任务都要动，并行就退化成排队。这类改动不进功能分支，由负责人走独立协调 PR 合入 `main`（SOP 红线 6 与 §4.6 判定表对 `tasks.yaml` 已经这么规定）。

**自检**：`tasks.yaml` 拆完后，立刻用 SOP §6.1 的并行管理提示词算一次就绪队列，看能同时开工几个任务。此刻重拆代价最小。

### 1.3 载体：`tasks.yaml`

上面三条判据不能停在口头判断，它需要一个文件。**Agent 无法自主规划长链路任务**，必须喂给它原子化、带依赖关系的步骤；同时这份文件正好逼着每个任务把三条判据填满。

**位置**：仓库根 `tasks.yaml`。**格式**：

```yaml
- id: T001
  title: 实现订单创建接口
  dependsOn: []
  pathSegment: 下单流程·步骤3                # 判据①：覆盖关键路径哪一段
  ruleRefs: [RULE-STOCK-001]                # 判据②：读取哪些规则
  operationRefs: [createOrder]              # 判据③：调用哪些 operationId
  specRefs: [contracts/order-api.yaml#/paths/~1api~1v1~1orders/post]
  acceptanceTests: [tests/order.spec.ts#createOrder]
  writeSet: [src/server/orders/create.ts]

- id: T002
  title: 前端订单表单提交
  dependsOn: []                             # 契约已定，可对 mock 与后端并行
  pathSegment: 下单流程·步骤4
  ruleRefs: [RULE-STOCK-001]
  operationRefs: [createOrder]
  specRefs: [prototype.html#order-form, contracts/order-api.yaml#/paths/~1api~1v1~1orders/post]
  acceptanceTests: [tests/order.spec.ts#submitForm]
  writeSet: [src/client/orders/OrderForm.tsx]
```

**九个字段全部必填**。所有复数字段都用数组：`dependsOn`、`ruleRefs`、`operationRefs`、`specRefs`、`acceptanceTests`、`writeSet`。L1 四件套阶段没有③④，`ruleRefs` 与 `operationRefs` 一律填 `[]`；`specRefs` 至少指向①或②的锚点。L2 的接口任务必须填写 `operationRefs`。`acceptanceTests` 在进入本手册前已由⑥生成；`writeSet` 只列允许本任务修改的仓库相对路径，CI 以实际 diff 校验不得越界。唯一保留例外是根目录 `REWORK_LOG.md`：它不写进各任务 `writeSet`、不参与写集冲突，但只允许按 §5.2 七列格式追加新行，由独立 append-only 卡点校验；修改 / 删除旧行仍算越界。

**不设自然语言备注字段。**若某个任务需要一段文字解释 Agent 才做得对，说明规格本身有洞（业务理解偏差），该回上游补①②③④，而不是在任务里加注解。给任务开自然语言后门，等于把已经赶出去的歧义又请回来。

### 1.4 任务清单卡点

与规格卡点同批执行：

| 卡点 | 拦截什么 |
| :--- | :--- |
| `ruleRefs` 中每个 id 存在于③；L1 必须为 `[]` | 悬空规则引用 |
| `operationRefs` 中每个 id 存在于④；L1 必须为 `[]` | 悬空接口引用 |
| `specRefs` 的每个锚点在目标文件中可解析 | 指向已删除的接口 / 元素 / 类型 |
| `acceptanceTests` 的每个用例在⑥中真实存在 | 无验收的任务、悬空用例引用 |
| `dependsOn` 无环、无指向不存在的 id | 死锁与断链 |
| 每条③的规则至少被一个任务的 `ruleRefs` 覆盖 | 规格里有规则却没人实现 |
| 除 `REWORK_LOG.md` 的七列只追加新行外，实际 diff 全部落在当前任务的 `writeSet` 内；并行任务写集不相交 | 越界修改与合并冲突；账本例外不得被用作通用后门 |
| PR / commit 的 `Task-ID` 所指任务，其 `dependsOn` 已全部完成 | 带着未满足的前置依赖抢跑 |

这些卡点与前册 A 组同批运行，因此进入开发手册时，任务引用和验收用例已经是稳定输入。任务是否开工不再由“用例是否存在”判断，而由 CI 是否收到关联该任务的 `Task-ID: Txxx` 并首次执行其验收用例判断。

## 二、做：单任务的固定四步

任务拆好了，每个任务内部按同一个顺序推进，**不可交换**：

```
契约  →  测试  →  实现  →  闸门
```

| 步 | 做什么 | 关键纪律 |
| :- | :--- | :--- |
| **契约** | 按 `tasks.yaml` 中本任务条目逐字段核对：②类型，以及适用时的③规则、④接口均已定义 | Agent **只能实现契约，不能自行发明**。L1 的③④显式不适用；其余缺口回上游补（原则 2），不在代码里绕过 |
| **测试** | 在当前 `Task-ID` 下首次执行⑥中预写的本任务用例，确认因目标能力尚未实现而失败（先红） | 用例绑定①的 `data-testid` 与适用时的③ `RULE-xxx`；若用例意外已绿，先确认任务是否多余或验收是否过弱，不直接进入实现 |
| **实现** | 写代码让测试变绿 | ⑤是硬约束不是建议；实现期间不许改测试来迁就代码 |
| **闸门** | 当前 `Task-ID` 的 A 组 + 适用 B 组卡点全绿 | 全绿才算做完；CI 必须列出启用 / 跳过项及理由。其他并行任务在各自分支上的红灯不污染本任务结论 |

**为什么顺序不能换**：先写实现再首次执行或补强测试，测试就容易照着实现取舍，验收退化为自我确认；先写实现再补契约，契约就变成实现的事后描述，②③④全部失去权威性。**顺序错了，后面每一步都在为前一步的模糊买单。**

**契约步发现缺口时的正确动作**：停下，回前一册第五章的规格循环补齐，等 A 组卡点重新全绿再回到本步。不要"先按理解写着，回头再补规格"——回头补的规格一定是照着代码写的，等于用实现污染了单一事实来源。

## 三、看：进度与排期

`tasks.yaml` 定义了要做什么，四步定义了怎么做。这一章回答第三个问题：**现在到哪了，还要多久。**

两者的共同点是：**都从证据推导，都不接受申报。**

### 3.1 进度：推导，不申报

`tasks.yaml` 里**没有 status 字段**，这是刻意的，理由两条：

- 规格应当稳定，状态是易变量。混在一起，Agent 每次读任务清单都在读一份不停变动的文件
- 更要紧的是：Agent 自己写 `status: done` 就是**自述**，而 §4.3 的纪律是**审核证据，不审自述**。让被审核方填写审核结论，闸门就是摆设

所以进度由 CI **从 `Task-ID` 关联事件、依赖图和闸门证据推导**，四态：

| 状态 | 判据（全部机器可测） |
| :--- | :--- |
| **已完成** | 当前任务的 `acceptanceTests` 全部通过，且关联提交的 A 组与适用 B 组卡点全绿 |
| **阻塞** | 自身未完成，且 `dependsOn` 中存在未完成项；CI 拒绝为它建立开工事件 |
| **进行中** | 依赖已满足，且已有 `Task-ID` 关联的首次 CI 执行记录，但尚未达到“已完成” |
| **未开始** | 依赖已满足，但还没有 `Task-ID` 关联的 CI 执行记录 |

"已完成"刻意与 §2 闸门步用**同一个判据**——都是卡点全绿，不是"测试绿就算完"。若只看用例通过，会出现某任务测试绿但性能预算红、进度显示已完成而闸门说没完成的裂缝。判据同源，就**不会出现"Agent 说完成但看板没动"或反过来的情况**：它们是同一个事实的两种呈现，而不是两份需要对账的记录。

“进行中”由首次带 `Task-ID` 的 CI 执行识别，而不是由用例文件是否存在识别——用例在开发前就已存在。首次红灯必须在实现 diff 产生前通过一次独立 CI / workflow 运行留证；若历史里只有实现后的绿灯，没有先红记录，CI 不得把该任务推导为完成。

**输出**：与技术栈快照同批发布到文档站。项目外的人问"做到哪个功能了"，给同一个 URL；每条显示任务 id、标题、状态、以及阻塞时卡在哪个前置任务。

**若要用看板**（Linear / GitHub Projects），必须由 CI 从推导结果**单向生成**，看板只读——**禁止拖卡回写**。双向同步会让任务状态同时存在于两处，违反原则 1；卡片被拖动而测试未变时，看板显示的是愿望，不是事实。

### 3.2 排期：实测，不估算

`tasks.yaml` 里也没有 `estimateHours`，理由与没有 status 同源：估算是猜测，不是证据。

而且在 Agent 范式下，它估的还是**错的变量**——一个任务的墙钟时间主要由**审核轮次**和**你何时有空审**决定，不由代码量决定：规格干净时十分钟结束，规格有洞时来回三轮拖两天。更要紧的是估算误差**不独立**：任务超时的主因通常是上游规格有洞，而这会同时拖长该任务与它的全部下游。误差系统性同向，关键路径算出来会稳定偏乐观。

排期改由**已完成任务的实测数据**推出，所需字段全部已存在，无需新增：

| 要算什么 | 怎么算 | 数据来源 |
| :--- | :--- | :--- |
| 单任务实际耗时 | 首次带该 `Task-ID` 的 CI 执行 → 该任务适用卡点全绿 的时间差 | CI 历史，零人工输入 |
| 近期完成速率 | 最近 N 个已完成任务 ÷ 时间跨度 | 同上 |
| 预计剩余时间 | 剩余任务数 ÷ 完成速率 | `tasks.yaml` + §3.1 状态推导 |
| 关键路径 | `dependsOn` 的最长链，**以任务数为单位** | `tasks.yaml`，今天就能算 |

三条输出纪律：

- **给区间不给单点**：按历史耗时分布输出 50% 与 85% 分位，例如"剩余 12 个任务，50% 概率 9 天内完成，85% 概率 15 天内"。单一日期是在把方差藏起来
- **冷启动诚实标注**：前 5–10 个任务没有历史，直接写"数据不足，暂不预测"。此时估算同样不准，区别只在于我们不假装准
- **粒度均匀是前提**：§1.1 的边界判据本来就倾向产出粒度相近的任务，任务数因此才接近工时的预测力。若实测耗时分布极度分散，那是**边界没拆好的信号**，该回 §1 重拆，而不是加一个估算字段去补偿

## 四、修：返工纪律

**返工不是收尾阶段，是横切面——从第一个任务起就开着。**

理由是一个反直觉的事实：**六件套各自正确，不等于整体正确。** 项目的熵不长在单个交付物内部，而长在它们的接缝上——代码改了规格没跟、规则改了用例没补、类型改了契约没同步。这类漂移不触发任何单个文件的检查，所以才需要 CI 卡点 A3、A4 专门盯接缝，也需要下面这五条纪律。

### 4.1 前提：可定位

返工的第一个前提不是纪律，是**能不能查到现场**。错误信息、日志、留档必须足以还原现场——**Agent 排障时没有"我记得当时是这样"，只有日志里写着的那些。**

⑤附录中的日志字段 schema 就是为这一条服务的。开发期最低标准是：出错时能一眼看出是哪条 `RULE-xxx`、哪个 `operationId`、哪个 `data-testid` 出的问题；不适用的键显式为 `null`。三者能对上，返工就是查表；对不上，返工只能靠猜，而 Agent 猜错的成本比人高得多——它会自信地沿着错误方向改一整轮。

**这条要求上线后不降级**：线上错误统一携带六个键：`commit`、`taskId`、`ruleId`、`operationId`、`dataTestId`、`adr`；条件不适用时填 `null` 而不是删键，详见上线后手册第二章。标识链断在哪里，闭环就在哪里变成开环。

### 4.2 归因先于修复

出错先分类再动手，因为四类的处置完全不同——尤其"该改哪个文件"完全不同：

| 归因 | 判据 | 处置（改哪里） |
| :--- | :--- | :--- |
| **Agent 幻觉** | 实现偏离已经明确的规格，包括编造字段 / 接口 / 规则 id，以及普通编码错误、漏分支、边界处理错误 | 先按规格修实现并记录；同类第二次才补⑤禁止项或 `SEMANTIC_GUIDE.md`，**不动正确的业务规格** |
| **框架漏洞** | 错误来自 CI、生成器、schema、任务推导或流程机制本身的缺失 / 错配，而不是某次实现偏离 | 首次确认即修框架或加卡点；这是**唯一**不等待第二次即可新增卡点的归因 |
| **业务理解偏差** | 规格本身就写错了 | 回基础层改①②③，再向下同步；**不在代码里打补丁** |
| **外部环境失败** | 网络、权限、版本、配额、第三方平台 | 记录现场；若新增可观察行为或降级策略，分别回③⑥、ADR 或⑤附录定义，事故噪音本身不固化成通用编码规则 |

四类是**主归因，必须四选一**。三册行文中的「Agent 执行偏差」是「Agent 幻觉」在固化阈值语境下的同义词，同指本表第一类，不是第五类。另设“逃逸原因”回答错误为什么没有被现有闸门拦住，例如“B3 缺少边界用例”；它不替代主归因。一个普通编码错误即使因为测试缺口流到线上，主归因仍是 Agent 幻觉，逃逸原因才是闸门缺口；只有 CI / 生成器 / 流程机制自身造成错误时，主归因才是框架漏洞。

跳过归因直接修，最常见的后果是把"业务理解偏差"误判为"Agent 幻觉"——于是给 Agent 加了一条根本拦不住的规则，而错误的规格原封不动留在上游，下一个任务照样踩。

### 4.3 审核证据，不审自述

Agent 说"已完成""已修复"不构成完成，必须挂上：**命令 + 真实输出 + 在哪跑**。给不出这三样就不许用完成类措辞。

这条对 Agent 的自我汇报一视同仁：卡点没跑绿，就是没做完；文档检查、结构检查通过，不等于"测试通过"。检查类型不许混。

### 4.4 记录只追加

验证记录、决策记录（含⑤的 ADR）、返工记录只追加不覆盖。旧决策错了也留着，另起一条订正并注明取代关系。

覆盖会毁掉可追溯性：三个月后没人能回答"当时为什么这么定"，于是同一个决策被推翻、恢复、再推翻。

**并行开发时这条要加严：禁止行内 append。**对既有条目的任何修正或补充，一律新开条目并引用旧编号，不在原行内续写——行内续写会把冲突面从"两行相邻"放大成"同一行互改"，前者可机械合并，后者必冲突。

### 4.5 固化有阈值：执行偏差第二次才升级，框架漏洞首次即修

不是每个错误都该产生新规则。单次 Agent 幻觉改实现并记录即可；**同类 Agent 执行偏差第二次出现**，才写进⑤。确认属于框架漏洞时不等待复发——框架本身已经被证明存在确定性缺口，首次就修生成器 / 流程或加 CI 卡点。业务规格写错也应立即回权威源修正，但不因此新增通用编码规则。

若把每次偶发执行偏差都写进⑤，20 条上限会迅速击穿——而 Agent 面对一份塞满低频规则的规范时，整体遵守率反而下降。规则体系的价值来自密度，不来自条数；框架漏洞的即时修复针对的是确定性机制，不占用这个经验阈值。

**这条阈值有个前提：第一次必须被记下来。** 不记，就永远判断不出"这是第二次"，阈值机制等于不存在——所以下一章不是可选项。

## 五、记：账本与自检

上一章的五条纪律里，有三条（归因、只追加、固化阈值）都依赖同一样东西：**一本可数的账**。这一章给它载体，并给出验证整套方法是否真在运转的方式。

### 5.1 规格与账本是两类东西

六件套与 `tasks.yaml` 是**规格**——描述系统应该是什么样、要做哪些事，是 Agent 的输入，可以被改写。
本章的账本是**记录**——描述实际发生过什么，是判断的依据，**只能追加**。

两者生命周期相反，因此不能混放：规格里塞历史会让 Agent 读到过期信息；账本被改写则失去存在意义。

### 5.2 返工账本 `REWORK_LOG.md`

**位置**：仓库根，与代码同仓同 PR 提交。**开发期返工与线上故障记在同一张表**——同类 Agent 执行偏差跨阶段各出现一次就是第二次，分两本账会让固化阈值失效；框架漏洞不依赖计数，首次确认即修。

**格式**：一条一行，**在出错的当下记，不事后补**——事后补的记录会漏掉当时判断不出归因的那些，而那些恰恰是最该留的。主归因四选一；逃逸原因写实际漏过它的闸门或“未逃逸（开发期已拦截）”。

| 日期 | 现象 | 主归因 | 逃逸原因 | 涉及交付物 | 处置 | 同类第几次 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 2026-08-01 | 提交按钮库存为 0 时仍可点 | 业务理解偏差 | B3 用例照着错误规格执行，无法拦截 | ③ RULE-STOCK-001 | 回③改条件，向下同步⑥与实现 | 1 |
| 2026-08-05 | Agent 引用了不存在的 `order.discount` | Agent 幻觉 | 未逃逸（B1 已拦截） | ② | 修实现；同类第 2 次，补⑤禁止项 | 2 → 已固化 |

七列各有用途，一列都不能省：**主归因**支撑 §4.2，**逃逸原因**明确哪道闸门失守，**同类第几次**支撑 §4.5 阈值，**涉及交付物**支撑 §5.4 自检，其余三列用于还原现场。

**为什么不用 issue 或 commit message 代替**：它们按时间散落，无法回答"同类问题出现过几次"。账本的唯一价值就是让同类可数。

### 5.3 不需要另建的账本

以下三样在大型项目里常见，但在轻量场景下**不要建**，否则违反单一事实来源：

| 常见做法 | 为什么不建 | 已有替代 |
| :--- | :--- | :--- |
| **手工维护的**状态看板 | 手填状态与真实状态必有一处过期；进度该从测试结果推导，不该由人或 Agent 申报 | §3.1 的进度快照（CI 推导生成） |
| 交付索引 | 六件套本身就是索引 | 前一册第二章总表与问题查找索引 |
| 对外汇报文档 | 面向人不面向 Agent，不进 Agent 上下文预算 | 单独治理，不受本方案约束 |

### 5.4 自检：这套方法真的在运转吗？

翻开 `REWORK_LOG.md`，随机挑一条最近的返工，回答三个问题：

1. 它属于**哪一类主归因**（§4.2 四选一）？ → 看「主归因」列
2. 当时**哪道卡点本应拦住**它，为什么漏过？ → 直接看「逃逸原因」，不从主归因猜
3. 处置是否符合阈值：Agent 执行偏差是否到同类第二次才固化，框架漏洞是否首次就修？ → 看「主归因」「同类第几次」「处置」三列

**三问答案必须从账本读出来，不靠回忆。** 需要回忆才能答的那一条，说明当时记漏了格——补记它，并检查是不是整段时间的记录都在漏同一格。

三问全答得上，说明这套方法在真实运转；答不上，说明返工只停在"修好了"，没有回流成结构——下次同一个坑还会再踩一遍。

---

**收束**：五个动作合起来是一句话——**按边界拆开，按顺序做完，从证据看进度，按归因修错，把教训记成可数的账。**

前一册让需求变成机器可读的规格，本册让规格变成可验证的代码。全程没有一份"给人阅读理解的技术方案"：Agent 拿到的是可执行规格，不是散文。

**下一步**：代码达到发布条件后，先完成《Agent-first·3·上线后运维与迭代手册》§1 的上线设施就位；首次发布后执行其 §2–§4——那里管的是线上问题怎么诊断，以及真实反馈如何合法地回到种子文档或 ADR。

**结构本身不产生正确性——它只是让错误有固定的位置可以被发现。**
