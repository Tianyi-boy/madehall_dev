## 二、裁决规则

**事实源顺位**：负责人当场裁决 ＞ I1 PRD ＞ I2 手册 ＞ I3 原型（仅作参照，其数值与文案不构成需求依据）。I2 与 I1 冲突时由负责人裁决谁胜出。

**冲突四分类与去向**：

| 类型 | 去向 |
| :- | :--- |
| 数值冲突 | 负责人当批裁决 → 修订落点文档 |
| 口径冲突（同一事实两种表述） | 负责人当批裁决 → 统一表述 |
| 单侧缺失 | 负责人裁决补入哪一侧 |
| 双侧未定 | 负责人当批裁决 → 双侧增加表述 |

**终态约定**：定稿后种子文档＋六件套为唯一活文档；I1–I4 标注"已冻结·历史输入"，此后需求变更只改种子文档与六件套，不回改传统文档。

## 三、流程与闸门

```
P0 本 SOP 定稿
      │ G0：负责人认可本 SOP
      ▼
P1 在项目根目录生成第一阶段 AGENTS.md
      │ G1：负责人审核通过，根目录 AGENTS.md 就位
      ▼
P2 咬合核查：I1 ↔ I2 逐维比对 → 登记表 → 负责人裁决 → 修订 I1/I2
      │ G2：登记表冲突清零，I1→PRD vFinal（REQ-ID 已固化），I2→手册 vFinal
      ▼
P3 生成 AI 需求种子文档（五节）
      │ G3：check-req-coverage --phase=p3 退出码 0 + 负责人视图审核通过
      ▼
P4 六件套生成（按 L2 六件套执行）：③②① 并行 → ④ → ⑤⑥；搭 A 组卡点
      │ G4：A 组卡点全绿（Y>0 时按 §7.4 标注「含 Y 项未验收」）+ 负责人视图审核通过
      ▼
P5 规格定稿冻结（参数定稿另计，见 §7.4）
```

闸门未过不得开工下一阶段；闸门内返工不算流程倒退。

## 四、P1 生成第一阶段 AGENTS.md

**R**：项目根目录 `AGENTS.md`（本体，唯一活文件）。
**W**：G0 过后启动。

阶段归档在 P5 执行（见 §4.4），归档件命名 `<本 SOP 文件名>-AGENTS.md`，与 SOP 一一对应。

### 4.1 取材

- **指导手册**：三原则的执行形式、六件套规范要点、A 组卡点、Agent 执行规范（局部修改指令四要素、防幻觉机制、变更影响申报）、⑤对 `AGENTS.md` 自身的约束。
- **本 SOP**：阶段与闸门、输入与产出路径、裁决规则、两份登记表的用法。

### 4.2 写作约束

- 正文规则 ≤ 20 条；需要更多时按目录分层另置局部规范，不扩容单文件。
- 只收本阶段（规格构建）用得上的约束；写代码、返工、提交类约束不进本版。
- 正文限标准 Markdown（CommonMark / GFM），不使用 Obsidian 私有语法。
- 附录·运行时事实单列，不计入 20 条。

### 4.3 必含条目

| # | 条目 | 内容要点 |
| :- | :--- | :--- |
| 1 | 角色边界 | Agent 改源文件；负责人只在渲染视图上审核与批注；派生视图任何人不手改 |
| 2 | 事实源顺位 | 同本 SOP 第二章；冲突登记后交负责人裁决，不静默采信 |

### 4.4 落盘与归档纪律

- **本体**＝项目根目录 `AGENTS.md`，全程唯一活文件；Agent 直接在此生成与修改，负责人在此审核。仓库内不存在第二份活的 `AGENTS.md`。

**R**：种子文档，固定五节。
**W**：G2 过后启动。

### 6.1 五节取材与分流

| 节 | 取材 | 分流规则 |
| :- | :--- | :--- |
| 1 业务目标 | PRD §1.1 | 一句话定位＋至多 3 条可量化指标；竞品与背景类内容不进 |
| 2 核心实体 | PRD §1.3、§3、§6–§9 | 只列实体名＋关键字段＋关系（伪代码）；字段完整定义归② |
| 3 关键路径 | 手册 12 大路径中的客户价值路径（准入 / T1 散买 / T2 散单 / T3 RFQ / FF&E 套餐 / FF&E 自组） | 内部治理线（权限 / 主数据 / 审计 / 客服例外）不进本节，归③与⑥权限矩阵 |
| 4 非 UI 能力清单 | PRD 全文扫描：webhook 幂等对账、自动开通链、激活邮件、魔法链接时效、催办提醒、参数变更重扫套餐、汇率快照、异常队列断点重试、AuditLog | 逐条列触发方式与结果；无遗漏（本节是④的第二输入源） |
| 5 量化验收指标 | PRD §13 参数台账＋性能与覆盖率预算 | 已落值的写入本节；未落值 🟡 项收进附录参数台账，保留"未落值不上线"红线 |

### 6.2 编写纪律

- 只答"做什么/为什么"，零实现细节；UI 描述零字。
- PRD §12 废止清单整体收编为附录"废止能力清单"，六件套生成时作反向校验：生成物中出现废止能力即返工。
- 占位符进②③④⑥时必须显式标注并与台账一一对应（标注方式见 §7.4）。

### 6.3 建立《未落值与待验证清单》

本阶段一并建台账，**不等到 P4**——P3 的脚本已要按它统计 Y。

- 路径：`docs/0.1种子文件(传统+AI)/未落值与待验证清单.md`；
- 来源：PRD vFinal §13 全部 🟡 项 ＋ 待验证技术项（如 Q004 Draft Order 锁价闭环）；
- 每条字段：编号（沿用 🟡 序号 / `SPIKE-n`）、内容、责任方、影响面（P3 时可留空，随②③④⑥生成逐步回填 `类型.字段` / `RULE-*` / `operationId` / `SPEC-*`）、阻断范围；
- 与种子附录参数台账的关系：种子附录只记"参数未落值"这一需求事实，台账是执行侧的跟踪表，编号一致、不重复记内容。

### 6.4 G3 追溯检查（脚本判定，负责人抽查）

**覆盖矩阵为机器可读文件**：`docs/0.1种子文件(传统+AI)/PRD覆盖矩阵.yaml`，每条一个 REQ-ID，字段固定：

```yaml
# 示例 1 · 有归宿的需求
- req_id: REQ-8.2-03
  prd_anchor: "#req-8-2-03"
  disposition: [seed, rule, spec]
  seed_section: 4
  rule_ids: [RULE-FFE-012]
  spec_ids: [SPEC-FFE-012-1]

# 示例 2 · 已废止的需求
- req_id: REQ-12-05
  prd_anchor: "#req-12-05"
  disposition: [dropped]
  drop_reason: "PRD §12 · 项目登记独家锁定"
```

| 字段 | 类型 | 必填条件 | 说明 |
| :--- | :--- | :--- | :--- |
| `req_id` | string | 恒必填 | 来自 PRD vFinal 锚点 |
| `prd_anchor` | string | 恒必填 | PRD vFinal 内锚点 |
| `disposition` | string[] | 恒必填非空 | 取值域＝`seed \| ui \| type \| rule \| api \| spec \| dropped` |
| `seed_section` | int 1–5 | 含 `seed` | 种子五节序号 |
| `ui_refs` | string[] | 含 `ui` | `文件#data-testid` |
| `type_refs` | string[] | 含 `type` | ②中的 `类型.字段` |
| `rule_ids` | string[] | 含 `rule` | ③中的 `RULE-*` |
| `api_refs` | string[] | 含 `api` | ④的 operationId |
| `spec_ids` | string[] | 含 `spec` | ⑥中的 `SPEC-*` |
| `drop_reason` | string | `disposition == [dropped]` | 指向种子附录废止清单条目 |

约束两条：**`disposition` 非空**；**`dropped` 与其余取值互斥**——一条需求要么有归宿，要么被废止，不得兼有，因此 `dropped` 行不出现其他 `*_refs`/`*_ids` 字段。

**校验脚本**：`scripts/check-req-coverage.mjs`，**必带 `--phase` 参数**，判据为退出码 0：

```bash
node scripts/check-req-coverage.mjs --phase=p3
```

`--phase` 取值 `p3 | p4 | p5`，决定启用哪几项检查——阶段规则写死在脚本里，不由 Agent 临场判断；未生成的交付物**跳过而非放行**，跳过项必须打印在输出里：

| 检查 | 内容 | p3 | p4 | p5 |
| :- | :--- | :-: | :-: | :-: |
| 1 schema 校验 | 每行字段齐全、`disposition` 非空且取值合法、`dropped` 互斥、条件必填项非空 | ✅ | ✅ | ✅ |
| 2 反向全覆盖 | PRD vFinal 每个 REQ-ID 在矩阵中恰好出现一次，缺失即孤儿 | ✅ | ✅ | ✅ |
| 3 正向可回指·seed | `seed_section` 对应的种子节内有该 REQ-ID 标注 | ✅ | ✅ | ✅ |
| 4 废止一致 | `dropped` 行的 `drop_reason` 匹配种子附录废止清单条目 | ✅ | ✅ | ✅ |
| 5 正向可回指·六件套 | `ui_refs`→①、`type_refs`→②、`rule_ids`→③、`api_refs`→④、`spec_ids`→⑥ 逐个真实存在 | 跳过 | ✅ | ✅ |
| 6 pending 一致 | ②`@pending`、③`status: pending_param`、④`x-status: pending-spike`、⑥`test.skip` 四处标记与《未落值与待验证清单》逐条对应 | 跳过 | ✅ | ✅ |

任一启用项不满足即非零退出并打印清单。**每次运行**（含 p3）必须打印三数：**已覆盖 X / 未验收 Y / 总 N**。Y 恒取自《未落值与待验证清单》（§6.3 已在 P3 建立，故 p3 运行时输入必然存在）；台账文件缺失时脚本直接失败，不得按 Y=0 处理。`--phase=p3` 下第 5、6 项标记为"本阶段跳过"，不得表述为通过。

负责人在 Obsidian 阅读视图审核种子文档全文，并抽查矩阵中 `dropped` 行是否确应废止。

### 7.4 未落值参数与待验证项（定稿边界）

**定稿分两级**：本 SOP 的 P5 收的是**规格定稿**（六件套结构完整、彼此自洽、A 组全绿）；**参数定稿**（🟡 清零、spike 结论落地）是上线前置，不是本 SOP 的收口条件。两者不得互相顶替。

**统一台账**：§6.3 已在 P3 建立的 `docs/0.1种子文件(传统+AI)/未落值与待验证清单.md`；本阶段随②③④⑥生成，把每条的影响面回填为具体的 `类型.字段` / `RULE-*` / `operationId` / `SPEC-*`。

**各件的处置规则（不得写死假值）**：

| 件 | 处置 |
| :- | :--- |
| ② | 受未决参数约束的字段加 JSDoc `@pending 🟡n`；**禁止**把猜测值写进字面量联合类型或 JSDoc 约束（如未定的枚举值、未定的上下限）；类型本身仍须可用，未决部分放宽而非编造 |
| ③ | 该规则标 `status: pending_param` ＋ `param_ref: 🟡n`；条件/动作中禁止填入猜测值 |
| ④ | 该 operationId 标 `x-status: pending-spike` 并注明待验证内容；不得声明未验证的响应结构为已定 |
| ⑥ | 写**参数化用例骨架**并标 `test.skip` ＋ 注释 `pending: 🟡n`；禁止用假值让用例变绿 |

**覆盖率口径（防"绿灯假象"）**：分母恒为规则/用例全集 N，不因 pending 缩小。报告一律呈现三数 **已覆盖 X / 未验收 Y / 总 N**（Y＝pending 条数），**禁止**用 `X/(N−Y)=100%` 的形式报告覆盖率。校验脚本第 6 项负责核对 Y 与台账逐条一致（编号或数量不符即红灯），并在每次 CI 输出中打印 pending 清单，不静默。

**红绿与 Y 的关系（不要混为一谈）**：pending 是**已登记的合法状态**，不使卡点变红——只要标记齐、与台账一致，A 组判绿。Y 是绿灯之上的附加信息，不是红灯条件。因此：

- **卡点结果**：A 组仍可全绿，G4／P5 的"全绿"判据可满足；
- **报告写法**：Y > 0 时报告标题必须写成「**A 组全绿 · 含 Y 项未验收**」，禁止只写"全绿"；pending 清单随报告呈负责人；
- **Y 归零的时点**：属参数定稿，不是本 SOP 的收口条件（见 §7.4 开头分级）。

**pending 功能进入实现的阻断**（防任务级假绿）：

- 默认**不拆任务**：pending 规则不得出现在 `tasks.yaml` 的 `ruleRefs`，`pending-spike` 的 operationId 不得出现在 `operationRefs`，相关功能不进实现步；
- 负责人批准先行开发时，该任务须标 `blockedBy: 🟡n` / `blockedBy: SPIKE-n`，且**三道卡点一并按"未验收"计**，不得按通过计：

  | 卡点 | 遇 pending 时的判定 |
  | :- | :--- |
  | B3 功能测试 | 对应 `test.skip` 用例计为未验收 |
  | B2 契约测试 | `x-status: pending-spike` 的 operationId 及其状态码不计入已覆盖，列入未验收 |
  | B5 权限矩阵 | 该 operationId × 各角色的格子同样计为未验收，不得因用例缺失而视作通过 |

  任务状态最多到"待验收"，**不得置为完成**；CI 输出必须列出该任务的全部 pending 项；
- 台账清零前，任何人不得把 skip 用例改成通过态；参数落值或 spike 结论落地后由责任方确认，再解除 skip 并重跑。
