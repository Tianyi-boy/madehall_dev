## 二、裁决规则

**事实源顺位**：负责人当场裁决 ＞ I1 PRD ＞ I2 手册 ＞ I3 原型（仅作参照，其数值与文案不构成需求依据）。I2 与 I1 冲突时由负责人裁决谁胜出。

**冲突四分类与去向**：

| 类型 | 去向 |
| :- | :--- |
| 数值冲突 | 负责人当批裁决 → 修订落点文档 |
| 口径冲突（同一事实两种表述） | 负责人当批裁决 → 统一表述 |
| 单侧缺失 | 负责人裁决补入哪一侧 |
| 双侧未定 | 负责人当批裁决 → 双侧增加表述 |

**终态约定**：定稿后种子文档＋六件套为唯一活文档；I1–I4 标注"已冻结·历史输入"，此后需求变更只改种子文档与六件套，不回改传统文档。

## 三、流程与闸门

```
P0 本 SOP 定稿
      │ G0：负责人认可本 SOP
      ▼
P1 生成第一阶段 AGENTS.md → 负责人复制到项目根目录
      │ G1：根目录 AGENTS.md 就位且与源文件哈希一致
      ▼
P2 咬合核查：I1 ↔ I2 逐维比对 → 登记表 → 负责人裁决 → 修订 I1/I2
      │ G2：登记表冲突清零，I1→PRD vFinal（REQ-ID 已固化），I2→手册 vFinal
      ▼
P3 生成 AI 需求种子文档（五节）
      │ G3：check-req-coverage 退出码 0 + 负责人视图审核通过
      ▼
P4 六件套生成（按 L2 六件套执行）：③②① 并行 → ④ → ⑤⑥；搭 A 组卡点
      │ G4：A 组卡点全绿 + 负责人视图审核通过
      ▼
P5 规格定稿冻结（参数定稿另计，见 §7.4）
```

闸门未过不得开工下一阶段；闸门内返工不算流程倒退。

### 5.4 修订纪律

- 业务裁决只由负责人做；Agent 只提供裁决建议＋两侧原文并排证据。凡改变业务事实（数值、口径、状态、权限）的修订，登记表"负责人裁决"列非空才可执行；Agent 可自行执行的仅限不改变业务事实的动作（版本号统一、告示核销、映射回写、格式修订）。
- 每批修订出一次 diff 供负责人在渲染视图核对。

### 5.5 REQ-ID 固化（G2 判据之一）

修订完成、PRD 出 vFinal 时，为每条需求性条目分配稳定编号 `REQ-<章节号>-<序号>`（如 `REQ-8.2-03`），以 HTML 锚点形式写入 PRD vFinal，编号只增不复用、不随章节调整重排。此后种子文档、③、⑥一律引用 REQ-ID，不引用章节号。

## 六、P3 生成 AI 需求种子文档

**R**：种子文档，固定五节。
**W**：G2 过后启动。

### 6.1 五节取材与分流

| 节 | 取材 | 分流规则 |
| :- | :--- | :--- |
| 1 业务目标 | PRD §1.1 | 一句话定位＋至多 3 条可量化指标；竞品与背景类内容不进 |
| 2 核心实体 | PRD §1.3、§3、§6–§9 | 只列实体名＋关键字段＋关系（伪代码）；字段完整定义归② |
| 3 关键路径 | 手册 12 大路径中的客户价值路径（准入 / T1 散买 / T2 散单 / T3 RFQ / FF&E 套餐 / FF&E 自组） | 内部治理线（权限 / 主数据 / 审计 / 客服例外）不进本节，归③与⑥权限矩阵 |
| 4 非 UI 能力清单 | PRD 全文扫描：webhook 幂等对账、自动开通链、激活邮件、魔法链接时效、催办提醒、参数变更重扫套餐、汇率快照、异常队列断点重试、AuditLog | 逐条列触发方式与结果；无遗漏（本节是④的第二输入源） |
| 5 量化验收指标 | PRD §13 参数台账＋性能与覆盖率预算 | 已落值的写入本节；未落值 🟡 项收进附录参数台账，保留"未落值不上线"红线 |

### 6.2 编写纪律

- 只答"做什么/为什么"，零实现细节；UI 描述零字。
- PRD §12 废止清单整体收编为附录"废止能力清单"，六件套生成时作反向校验：生成物中出现废止能力即返工。
- 占位符进②③⑥时必须显式标注并与附录参数台账一一对应。

### 6.3 G3 追溯检查（脚本判定，负责人抽查）

**覆盖矩阵为机器可读文件**：`docs/0.1种子文件(传统+AI)/PRD覆盖矩阵.yaml`，每条一个 REQ-ID，字段固定：

```yaml
- req_id: REQ-8.2-03          # 必填，来自 PRD vFinal 锚点
  prd_anchor: "#req-8-2-03"   # 必填
  disposition: seed | rule | spec | dropped   # 必填，归宿类型，可多值
  seed_section: 4             # disposition 含 seed 时必填（种子五节序号）
  rule_ids: [RULE-FFE-012]    # disposition 含 rule 时必填
  spec_ids: [SPEC-FFE-012-1]  # disposition 含 spec 时必填
  drop_reason: ""             # disposition = dropped 时必填（对应 PRD §12 废止清单条目）
```

**校验脚本**：`scripts/check-req-coverage.mjs`，在 P3 与 A 组卡点中各跑一次，判据为退出码 0：

```bash
node scripts/check-req-coverage.mjs
```

脚本必须做四件事，任一不满足即非零退出并打印清单：

1. **schema 校验**：矩阵每行字段齐全、`disposition` 取值合法、条件必填项非空；
2. **反向全覆盖**：PRD vFinal 中的每个 REQ-ID 在矩阵中恰好出现一次，缺失即孤儿；
3. **正向可回指**：种子文档每条断言标注的 REQ-ID 存在于 PRD vFinal；矩阵中引用的 `rule_ids`/`spec_ids` 在③/⑥中真实存在（P3 阶段③⑥尚未生成时，此项只校验 `seed`/`dropped` 两类，`rule`/`spec` 类留待 A3 复检）；
4. **废止一致**：`dropped` 行的 `drop_reason` 能匹配到种子附录废止能力清单条目。

负责人在 Obsidian 阅读视图审核种子文档全文，并抽查矩阵中 `dropped` 行是否确应废止。

## 七、P4 六件套生成

按 **L2 六件套**执行（①②③④⑤⑥ 全建，不走 L1）。

### 7.1 生成顺序

```
批次 1（基础层，可并行）：
  ③ 业务规则表  ← PRD vFinal 全部"条件→动作"断言
  ② 数据模型    ← 种子§2 实体 + PRD 字段级事实
  ① 语义化原型  ← I3（交互参照）＋手册核查项（覆盖清单）
批次 2（衍生层）：
  ④ API 契约    ← ①交互 + ②类型 + 种子§4 非 UI 清单（三处之外不得出现接口）
批次 3（约束层）：
  ⑤ AGENTS.md + adr/ + SEMANTIC_GUIDE.md
  ⑥ 验收标准    ← ③逐条覆盖 + ④权限矩阵 + 手册核查项转用例
```

**首次迁移例外（仅本 SOP 有效）**：指导手册规定种子文档为体系唯一输入；本次因存量文档迁移，①②③允许直接取材于 PRD vFinal 与手册 vFinal。适用边界三条：

1. 每处直接取材必须在生成物中标注来源（`<!-- src: REQ-x.y-nn -->` 或 YAML `src:` 字段），供 P5 逐处核查；
2. 凡直接取材而种子文档未承载的事实，**必须回流补进种子文档**（走 §7.5），使种子在 P5 时成为完整上游；
3. **P5 冻结后本例外失效**：此后一切生成只以种子文档＋六件套为输入，不得再引用 I1–I4。

### 7.2 各件要点（通用细则以指导手册第四章为准，此处只列本项目特有事项）

### 7.4 未落值参数与待验证项（定稿边界）

**定稿分两级**：本 SOP 的 P5 收的是**规格定稿**（六件套结构完整、彼此自洽、A 组全绿）；**参数定稿**（🟡 清零、spike 结论落地）是上线前置，不是本 SOP 的收口条件。两者不得互相顶替。

**统一台账**：`docs/0.1种子文件(传统+AI)/未落值与待验证清单.md`，收两类条目——🟡 未落值参数（来自 PRD §13）、待验证技术项（如 Q004 Draft Order 锁价闭环）。每条含：编号、影响的 `RULE-*` / `operationId` / `SPEC-*`、阻断范围、责任方。

**各件的处置规则（不得写死假值）**：

| 件 | 处置 |
| :- | :--- |
| ③ | 该规则标 `status: pending_param` ＋ `param_ref: 🟡n`；条件/动作中禁止填入猜测值 |
| ④ | 该 operationId 标 `x-status: pending-spike` 并注明待验证内容；不得声明未验证的响应结构为已定 |
| ⑥ | 写**参数化用例骨架**并标 `test.skip` ＋ 注释 `pending: 🟡n`；禁止用假值让用例变绿；这类用例不计入覆盖率分母，但必须在台账中可见 |

**阻断规则**：台账非空时，允许进入开发时手册的实现阶段，但 `pending_param` / `pending-spike` 覆盖到的功能**不得上线**；台账清零前，任何人不得把这些 skip 用例改成通过态。
