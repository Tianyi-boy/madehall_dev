## 二、事实源顺位（本流程的裁决规则）

《00-需求差异矩阵 v4.10》**不入库、不参与裁决**（2026-08-02 负责人裁决）——理由是 PRD 更新且矩阵内容已整理进 PRD，入库只会多出一个需持续同步的事实源。本流程内的顺位为：

1. **负责人当场裁决** —— 最高，一切冲突的终审；
2. **I1 PRD** —— 在库最高事实源（最新、由矩阵整理而来）；
3. **I2 手册** —— 路径与核查项事实源，与 I1 冲突时默认 I1 胜出、但**必须登记并经负责人确认**（不静默采信）；
4. **I3 原型** —— 仅作交互与视觉参照，**不作为任何需求事实的依据**（原型里的数值/文案与文档冲突时一律以文档为准）。

据此，P1 **不设**"矩阵 ↔ PRD"比对轮；任何一方引用矩阵条款而 PRD 未收编的，按"单侧缺失"登记并交负责人裁决。

**终态约定（先说死，避免返工）**：定稿后，种子文档＋六件套成为唯一活文档；I1/I2/I3/I4 全部标注"已冻结·历史输入"，此后一切需求变更只改种子文档与六件套，不再回改传统文档。这是指导手册原则 1（单一事实来源）的直接推论。

```
P0 本 SOP 定稿
      │ 闸门 G0：负责人认可本 SOP（四项前置裁决已写入正文：矩阵不入库 /
      │          ①重建 / 不做旧原型全量走查 / 金额门槛 US$5,000）
      ▼
P1 咬合核查：I1 ↔ I2 逐维比对 → 咬合差异登记表 → 负责人裁决 → 修订 I1/I2
      │ 闸门 G1：登记表冲突清零，I1→PRD vFinal，I2→手册 vFinal
      ▼
P2 生成 AI 需求种子文档（五节）
      │ 闸门 G2：追溯检查通过 + 负责人视图审核通过 → 种子 v1.0
      ▼
P3 六件套生成（L2 直上）：③②① 并行 → ④ → ⑤⑥；A 组卡点搭建

```

每个闸门都是"负责人拍板点"——闸门未过，下一阶段不得开工；闸门内的返工不算流程倒退。

冲突类型四分：**数值冲突 / 口径冲突（同一事实两种表述）/ 单侧缺失 / 双侧未定**。前三类由负责人当批裁决；"双侧未定"不在 P1 强行定，转入种子文档附录参数台账（🟡 项）或 `adr/`「暂未决定」，但必须显式挂账、不许留白。

### 4.3 修订纪律

- 裁决只由负责人做；Agent 只提供裁决建议＋证据（两侧原文并排）。
- 修订 I2 时一并完成：停用告示核销、49 条映射结果回写、文件名与内容版本号统一；**手册定位改为"路径事实清单"**——对旧原型的 12 大路径人工走查不再执行（2026-08-02 负责人裁决：原型既然重建，对旧原型的走查结论随之失效），走查操作类章节（0.1 启动服务器 / 0.4 演示控件 / 各条"点开核对"操作指引）标注"已废止·历史走查口径"；核查项本体全部保留，作为①覆盖清单与⑥用例的底稿。I4 走查登记表（空表）随传统文档一并冻结。
- 每批修订出一次 diff 供负责人在渲染视图核对。

## 五、P2 生成 AI 需求种子文档

**R**：`docs/0.1种子文件(传统+AI)/AI种子文件/Madehall-AI需求种子文档-v1.0.md`，固定五节。
**W**：G1 过后启动。

### 5.1 五节的取材来源与分流规则

| 节 | 取材 | 分流规则（防止种子文档变成第二份 PRD） |
| :- | :--- | :--- |
| 1 业务目标 | PRD §1.1 定位 | 一句话定位＋至多 3 条可量化指标；竞品/背景类内容不进 |
| 2 核心实体 | PRD §1.3、§3、§6–§9 中的名词 | 只列实体名＋关键字段＋关系（伪代码）；字段完整定义归②数据模型 |
| 3 关键路径 | 手册 12 大路径中的**客户价值路径**（准入 / T1 散买 / T2 散单 / T3 RFQ / FF&E 套餐 / FF&E 自组） | 内部治理线（权限 / 主数据 / 审计 / 客服例外）**不进关键路径**——它们是规则不是路径，归③业务规则表与⑥权限矩阵 |
| 4 非 UI 能力清单 | PRD 全文扫描：webhook 幂等对账、自动开通链、激活邮件、魔法链接时效、催办提醒、参数变更重扫套餐、汇率快照、异常队列断点重试、AuditLog | 逐条列出触发方式与结果；此节是④的第二输入源，漏一条④就少一组接口 |
| 5 量化验收指标 | PRD §13 参数台账＋性能/覆盖率预算 | **已落值的**写进本节；**未落值的 🟡 项**收进种子文档附录"参数台账"，保留"未落值不上线"红线，占位符进②③⑥时必须显式标注 |

### 5.2 种子文档纪律（照抄指导手册第三章）

- 只答"做什么/为什么"，零实现细节；UI 描述零字（由①承载）。
- PRD §12 废止清单整体收编为种子文档附录"废止能力清单"——这是防回退契约，六件套生成时作反向校验（生成物中出现废止能力即 bug）。

### 5.3 G2 追溯检查（Agent 机器执行，负责人抽查）

1. **正向**：种子文档每条断言能回指 PRD vFinal 章节；
2. **反向**：PRD vFinal 每个需求性条目在"种子文档 / ③规则表（预分配）/ ⑥验收（预分配）"三处至少有一个归宿——产出《PRD 覆盖矩阵》，孤儿条目=漏洞，当场补；
3. 负责人在 Obsidian 阅读视图审核种子文档全文。

## 六、P3 六件套生成

**级别判定：L2 直上，不走 L1。** 三个升级触发条件全部命中：规则条数远超 10（PRD 提取预估 60+）；前后端分离（Shopify + 自研 FF-DB + BFF）；存在非 UI 后端能力（webhook / 定时 / 批处理）。

### 6.1 生成顺序与依赖

```
批次 1（基础层，可并行）：
  ③ 业务规则表  ← PRD vFinal 全部"条件→动作"断言
  ② 数据模型    ← 种子§2 实体 + PRD 字段级事实
  ① 语义化原型  ← 统一原型（交互参照）＋手册路径（覆盖清单）
批次 2（衍生层）：
  ④ API 契约    ← ①交互 + ②类型 + 种子§4 非 UI 清单（三处之外不得出现接口）
批次 3（约束层）：
  ⑤ AGENTS.md + adr/ + SEMANTIC_GUIDE.md ← PRD §1.2 技术契约 + 生成过程中的决策
  ⑥ 验收标准    ← ③逐条覆盖 + ④权限矩阵 + 手册核查项转用例
```

### 6.2 各件要点（细则以指导手册第四章为准，此处只记本项目特有事项）

| 件 | 本项目特有事项 |
| :- | :--- |
| ③ | 规则命名 `RULE-<域>-<序号>`（域=准入/T1/T2/T3/FFE/PRICE/PERM/AUDIT）；四眼、门控、成立三条件、状态转移白名单全部入表；未落值参数以 `param_ref: 🟡n` 占位并被 A2 检出提示 |
| ② | 实体含：商户申请、Company 映射、参考变体、RFQ、取材表、CADVersion、Quote（版本链）、项目容器、套餐模板、SO/SC、成本八项、六表主数据、Factory 锚点、AuditLog；金额一律用分、时间一律毫秒 |
| ① | **重建，不就地改造**（2026-08-02 负责人裁决；旧统一原型的三稿以转义字符串内嵌单文件，工具不可达、diff 不可读、无法挂 rule-id/testid）：以统一原型为视觉/交互参照，按 A/B/C 三域分文件新建语义化原型；`data-rule-id` 挂③、`data-testid` 供⑥；手册 12 大路径的每个核查项映射为原型覆盖清单，替代旧走查。旧原型冻结留档，只作参照 |
| ④ | 错误码与 `RULE-*` 建映射；Shopify 侧边界（S 域）只建"跳转/回调"契约不复刻 Shopify API；Q004（Draft Order 锁价闭环）在④中标注"待 spike 验证"而非假装已定 |
| ⑤ | ADR 七类起草为 `adr/draft-*.md`；PRD §1.2 已隐含至少：双系统分工、OAuth/PKCE+BFF、metafield 命名空间、状态机白名单+AuditLog、金额单一算法、文件私有存储+签名 URL——逐条转正式 ADR；未定的（如 3D 格式⑬②）写「暂未决定」 |
| ⑥ | 手册 12 大路径核查项逐条转为 spec 用例骨架（每条注释回指手册条目号与 RULE-id）；权限矩阵 = ④operationId × 七角色；性能预算与覆盖率阈值取种子§5 |

### 6.3 A 组卡点搭建（本阶段唯一要建的 CI）

A1 构建型视图重建、A2 ③schema 校验+冲突检测、A3 规则引用完整性（①↔③↔⑥）、A4 ④与②同源比对。B 组不在本 SOP 范围（进开发时手册再启用）。

### 6.4 漏洞回流（P3 期间的唯一返工通道）

生成下游时发现上游缺漏（种子少一条非 UI 能力、PRD 两义、手册路径缺步骤）：

- **禁止就地补**——登记进《漏洞回流登记表》（同咬合登记表格式＋"回流层级"列），回上游改，再重新生成下游；
- 涉及需求裁决的，攒批提交负责人，**不逐条打断**；
- 种子/PRD vFinal 因回流产生的修订，版本号递增并在文档头记一行变更日志。
