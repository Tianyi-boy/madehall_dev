## 二、裁决规则

**事实源顺位**：负责人当场裁决 ＞ I1 PRD ＞ I2 手册 ＞ I3 原型（仅作参照，其数值与文案不构成需求依据）。I2 与 I1 冲突时默认 I1 胜出，但必须登记并经负责人确认，不静默采信。

**冲突四分类与去向**：

| 类型 | 去向 |
| :- | :--- |
| 数值冲突 | 负责人当批裁决 → 修订落点文档 |
| 口径冲突（同一事实两种表述） | 负责人当批裁决 → 统一表述 |
| 单侧缺失 | 负责人裁决补入哪一侧 |
| 双侧未定 | 不在 P1 强定；挂种子文档附录参数台账（🟡 项）或 `adr/`「暂未决定」，不留白 |

**终态约定**：定稿后种子文档＋六件套为唯一活文档；I1–I4 标注"已冻结·历史输入"，此后需求变更只改种子文档与六件套，不回改传统文档。

## 三、流程与闸门

```
P0 本 SOP 定稿
      │ G0：负责人认可本 SOP
      ▼
P1 咬合核查：I1 ↔ I2 逐维比对 → 登记表 → 负责人裁决 → 修订 I1/I2
      │ G1：登记表冲突清零，I1→PRD vFinal，I2→手册 vFinal
      ▼
P2 生成 AI 需求种子文档（五节）
      │ G2：双向追溯检查通过 + 负责人视图审核通过
      ▼
P3 六件套生成（按 L2 六件套执行）：③②① 并行 → ④ → ⑤⑥；搭 A 组卡点
      │ G3：A 组卡点全绿 + 负责人视图审核通过
      ▼
P4 定稿冻结
```

闸门未过不得开工下一阶段；闸门内返工不算流程倒退。

## 五、P2 生成 AI 需求种子文档

**R**：种子文档，固定五节。
**W**：G1 过后启动。

### 5.1 五节取材与分流

| 节 | 取材 | 分流规则 |
| :- | :--- | :--- |
| 1 业务目标 | PRD §1.1 | 一句话定位＋至多 3 条可量化指标；竞品与背景类内容不进 |
| 2 核心实体 | PRD §1.3、§3、§6–§9 | 只列实体名＋关键字段＋关系（伪代码）；字段完整定义归② |
| 3 关键路径 | 手册 12 大路径中的客户价值路径（准入 / T1 散买 / T2 散单 / T3 RFQ / FF&E 套餐 / FF&E 自组） | 内部治理线（权限 / 主数据 / 审计 / 客服例外）不进本节，归③与⑥权限矩阵 |
| 4 非 UI 能力清单 | PRD 全文扫描：webhook 幂等对账、自动开通链、激活邮件、魔法链接时效、催办提醒、参数变更重扫套餐、汇率快照、异常队列断点重试、AuditLog | 逐条列触发方式与结果；无遗漏（本节是④的第二输入源） |
| 5 量化验收指标 | PRD §13 参数台账＋性能与覆盖率预算 | 已落值的写入本节；未落值 🟡 项收进附录参数台账，保留"未落值不上线"红线 |

### 5.2 编写纪律

- 只答"做什么/为什么"，零实现细节；UI 描述零字。
- PRD §12 废止清单整体收编为附录"废止能力清单"，六件套生成时作反向校验：生成物中出现废止能力即返工。
- 占位符进②③⑥时必须显式标注并与附录参数台账一一对应。

### 5.3 G2 追溯检查（Agent 执行，负责人抽查）

1. **正向**：种子文档每条断言可回指 PRD vFinal 章节；
2. **反向**：PRD vFinal 每个需求性条目在"种子文档 / ③（预分配）/ ⑥（预分配）"三处至少有一个归宿，产出《PRD 覆盖矩阵》，孤儿条目当场补；
3. 负责人在 Obsidian 阅读视图审核种子文档全文。

## 六、P3 六件套生成

按 **L2 六件套**执行（①②③④⑤⑥ 全建，不走 L1）。

### 6.1 生成顺序

```
批次 1（基础层，可并行）：
  ③ 业务规则表  ← PRD vFinal 全部"条件→动作"断言
  ② 数据模型    ← 种子§2 实体 + PRD 字段级事实
  ① 语义化原型  ← I3（交互参照）＋手册核查项（覆盖清单）
批次 2（衍生层）：
  ④ API 契约    ← ①交互 + ②类型 + 种子§4 非 UI 清单（三处之外不得出现接口）
批次 3（约束层）：
  ⑤ AGENTS.md + adr/ + SEMANTIC_GUIDE.md
  ⑥ 验收标准    ← ③逐条覆盖 + ④权限矩阵 + 手册核查项转用例
```

### 6.2 各件要点（通用细则以指导手册第四章为准，此处只列本项目特有事项）

| 件 | 本项目特有事项 |
| :- | :--- |
| ③ | 规则命名 `RULE-<域>-<序号>`（域＝准入/T1/T2/T3/FFE/PRICE/PERM/AUDIT）；四眼、门控、成立三条件、状态转移白名单全部入表；未落值参数以 `param_ref: 🟡n` 占位 |
| ② | 实体覆盖：商户申请、Company 映射、参考变体、RFQ、取材表、CADVersion、Quote（版本链）、项目容器、套餐模板、SO/SC、成本八项、六表主数据、Factory 锚点、AuditLog；金额一律用分、时间一律毫秒 |
| ① | **重建**，按 A/B/C 三域分文件新建语义化原型，不改造 I3；`data-rule-id` 挂③、`data-testid` 供⑥；手册每个核查项映射为原型覆盖清单 |
| ④ | 错误码与 `RULE-*` 建映射；S 域只建跳转与回调契约，不复刻 Shopify API；Q004（Draft Order 锁价闭环）标注"待 spike 验证" |
| ⑤ | ADR 七类起草为 `adr/draft-*.md`；PRD §1.2 逐条转正式 ADR（双系统分工、OAuth/PKCE+BFF、metafield 命名空间、状态机白名单+AuditLog、金额单一算法、文件私有存储+签名 URL）；未定项写「暂未决定」 |
| ⑥ | 手册核查项逐条转 spec 用例骨架，每条注释回指手册条目号与 `RULE-*`；权限矩阵＝④operationId × 七角色；性能预算与覆盖率阈值取种子§5 |

### 6.3 A 组卡点搭建

A1 构建型视图随源文件重建；A2 ③ JSON Schema 校验＋规则冲突检测；A3 规则引用完整性（①↔③↔⑥）；A4 ④与②同源比对。B 组不在本 SOP 范围。

### 6.4 漏洞回流

生成下游时发现上游缺漏：

- 禁止就地补；登记进《漏洞回流登记表》（同 4.2 格式＋"回流层级"列），回上游改后重新生成下游；
- 涉及需求裁决的攒批提交负责人，不逐条打断；
- 种子或 PRD vFinal 因回流修订时，版本号递增并在文档头记一行变更日志。
