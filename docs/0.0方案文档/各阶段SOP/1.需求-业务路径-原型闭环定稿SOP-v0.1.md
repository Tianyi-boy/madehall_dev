# Madehall｜需求—业务路径—原型闭环定稿 SOP

> **版本**：v0.1（磨合草案）  
> **状态**：待负责人审核；未定稿前只用于讨论流程，不作为执行依据  
> **适用阶段**：传统 PRD 已存在、六要素尚未创建  
> **目标**：先使 PRD 与业务路径双向咬合，再由负责人按路径人工走查统一原型，闭环修复三份文档，达到进入六要素创建环节的条件。

---

## 1. 本轮对象与事实源顺序

| 层级 | 文件 | 定位 | 允许定义什么 | 不允许做什么 |
|---|---|---|---|---|
| 1 | `Madehall_PRD.md` | 本阶段唯一需求事实源 | 做什么、为什么、业务规则、角色、状态、参数及待定项 | 写具体页面实现细节 |
| 2 | `1-业务路径核查手册-v1.3.md` | PRD 的可执行业务路径视图 | 只引用 PRD，展开前置条件、动作、结果、分支和核查步骤 | 独立发明或改判业务规则 |
| 3 | `Madehall_unified_prototype_ZH.html` | 可交互原型实现 | 实现 PRD 与路径中适用于原型的界面和交互 | 反向定义需求；掩盖未裁决口径 |
| 账本 | `2.2-负责人走查问题登记表-v2.0.md` | 问题与证据账本 | 记录现象、裁决、修改、验证、复验 | 充当第四份需求文档 |

硬规则：

1. 修改顺序固定为 **PRD → 业务路径 → 原型 → 问题账本**。
2. 下游发现上游缺口，必须回上游修；禁止在路径或原型中先打补丁。
3. 负责人验证业务合理性；Agent 负责定位、编辑、确定性检查和证据登记。
4. 行号只用于当次定位；长期追溯使用稳定 ID，避免编辑后行号漂移。
5. 本轮不创建六要素文件；三文档定稿后再按《Agent-first·1·开发前规格构建方案》进入下一阶段。

## 4. 总流程

```text
冻结输入
  ↓
PRD 原子化与自洽检查
  ↓
业务路径重建并逐条挂 PRD 锚点
  ↓
双向覆盖核查（PRD → 路径；路径 → PRD）
  ↓
负责人按路径走统一原型并登记问题
  ↓
逐条裁定责任层
  ↓
按 PRD → 路径 → 原型 修复
  ↓
机器检查 + 负责人原路径复验
  ↓
三文档定稿 → 进入六要素创建
```

不得跳步：文档尚未咬合时走原型，只会把“路径写错”和“原型做错”混在同一批问题里。

## 5. 分阶段 SOP

### S0｜冻结本轮输入

- **W｜触发时机**：SOP 定稿、准备启动第一轮时。
- **A｜行动**：
  1. 在四份文件头部统一写明当前文件名、版本、日期和事实源顺序。
  2. 业务路径手册移除旧矩阵、旧三原型、旧目录和“部分条目暂停使用”的运行口径；旧沿革只保留为历史说明，不能与当前规则混排。
  3. 问题登记表更新为本 SOP 第 1 节列出的四个文件。
  4. 计算四个文件的 SHA-256，登记为“走查基线”；正式走查期间每次修复形成新批次，不覆盖基线记录。
- **R｜结果**：所有参与者面对同一批文件，任何问题可还原到明确基线。
- **卡点 G0**：文件名、版本、事实源、原型 URL 任一不一致即停止。

基线命令（Agent 执行并把真实输出写入问题账本）：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath `
  "Madehall_PRD.md", `
  "1-业务路径核查手册-v1.3.md", `
  "Madehall_unified_prototype_ZH.html", `
  "2.2-负责人走查问题登记表-v2.0.md"
```

### S1｜PRD 原子化与内部自洽

- **W｜触发时机**：G0 通过后；任何需求裁决改变时重新触发。
- **A｜行动**：
  1. 为每条可独立判断真假的需求分配稳定 ID：`PRD-章节-序号`，例如 `PRD-08-006`。
  2. 一条同时包含多个条件、动作或例外的长句，拆成多个原子需求；语义不改，只拆结构。
  3. 每条标记类型：`UI`、`业务路径`、`非 UI 能力`、`权限`、`状态/数据`、`参数待定`、`技术验证`、`已废止`。
  4. 建立六份词表并在 PRD 内各自只定义一次：角色、实体/单号、状态、关键数值、统一术语、废止能力。
  5. 核查同一概念是否在不同章节出现不同值、不同状态名、不同责任角色或不同边界。
  6. 待定项必须写清：负责人、最晚裁决时机、未裁决影响；不得用含混文字假装已定。
- **R｜结果**：PRD 中每条需求可被唯一引用、可判断、无未标记冲突。
- **卡点 G1**：以下任一存在即不进入 S2：
  - 同一业务事实有两个有效值；
  - 规则只有描述，没有适用条件或例外边界；
  - 待定项没有责任人或触发时机；
  - 已废止能力仍出现在有效需求中。

### S2｜业务路径重建并挂接 PRD

- **W｜触发时机**：G1 通过；PRD 的业务路径、角色、状态或规则变化时重新触发。
- **A｜行动**：
  1. 保留现有 `1.1-01` 一类路径编号作为稳定 `PATH-ID`；重复或失效编号重排一次后冻结。
  2. 每个路径步骤统一写成六字段：
     - `PRD 引用`：一个或多个 `PRD-ID`；
     - `前置`：角色、登录态、数据态、页面态；
     - `动作`：负责人实际执行的单一动作；
     - `预期`：可观察结果；
     - `分支/例外`：失败、拒绝、取消、回退、权限不足等；
     - `原型边界`：可真实演示、仅占位、不可模拟。
  3. 删除或重写所有停用条目，不使用“先跳过、以后统一改”的临时告示作为有效路径。
  4. 统一原型的 A/B/C 域通过一个 URL 和内部导航走查；演示函数只作为到达特定状态的辅助，不替代真实路径步骤。
  5. 在路径手册附录生成“PRD → PATH 覆盖索引”，只写 ID 和覆盖类别，不复制规则正文。
- **R｜结果**：路径中的每个动作都能回指 PRD；路径手册不再拥有独立业务规则。
- **卡点 G2**：任一路径步骤无 PRD 引用，或其预期超出 PRD，立即回 S1，不得自行补齐。

路径步骤推荐模板：

```markdown
- [ ] PATH-3.2-04｜选择完整配置后提交询价
  - PRD：PRD-06-002、PRD-06-004
  - 前置：active 商户；Tier2 可售；配置尚未选全
  - 动作：补齐最后一个配置项并点击“提交询价”
  - 预期：按钮由禁用变可用；提交后创建 pricing 态询价单
  - 分支/例外：组合不存在时选项置灰并解释；无确认价仍可提交
  - 原型边界：创建演示记录；不发送真实通知
```

### S3｜PRD 与路径双向咬合核查

- **W｜触发时机**：路径首轮重建后；之后任一 PRD 或路径变更时。
- **A｜行动**：执行两次独立扫描：
  1. **正向覆盖**：每条 `UI/业务路径/权限/状态` 类 PRD，至少映射到一个 `PATH-ID`；确实不能在原型验证的，必须标 `非 UI` 或 `原型限制` 并说明后续六要素载体。
  2. **反向合法性**：每个 `PATH-ID` 至少引用一个有效 `PRD-ID`；预期、角色、状态、数值和例外均不得超出引用内容。
  3. 对六类横切口径逐项对照：角色权限、状态机、关键数值、实体/单号、统一术语、废止能力。
  4. 差异只分为：`PRD 缺口`、`PRD 内部冲突`、`路径漏项`、`路径误读`、`非 UI`、`原型限制`。
  5. PRD 缺口或冲突交负责人裁决；裁决后先改 PRD，再同步路径索引。
- **R｜结果**：形成双向全覆盖，且“未覆盖”均有明确合法原因。
- **卡点 G3**：
  - `UI/业务路径/权限/状态` 类 PRD 无路径归宿数＝0；
  - 无 PRD 来源的路径步骤数＝0；
  - 未裁决冲突数＝0；
  - 未解释覆盖缺口数＝0。

### S4｜准备人工走查

- **W｜触发时机**：G3 通过后；每个修复批次开始复验前。
- **A｜行动**：
  1. Agent 更新问题登记表头部、状态定义和逐条模板。
  2. Agent 启动当前目录的本地服务器，并确认统一原型能打开。
  3. 负责人使用固定浏览器、固定窗口宽度、固定角色和固定演示数据；每条路径开始前按手册复位。
  4. 问题登记表记录本批次 PRD、路径、原型的 SHA-256。
- **R｜结果**：走查环境和输入可复现。
- **卡点 G4**：页面打不开、控制台存在阻塞错误、基线哈希未登记，均不开始走查。

推荐启动命令：

```powershell
python -m http.server 8900 --bind 127.0.0.1 --directory "D:\madehall_dev\docs\0.1种子文件(传统+AI)\传统种子文件"
```

负责人打开：

```text
http://127.0.0.1:8900/Madehall_unified_prototype_ZH.html
```

### S5｜负责人按业务路径走查并登记

- **W｜触发时机**：G4 通过；首次全量走查或修复后的定向复验。
- **A｜行动**：
  1. 按 `大路径 1 → 12 → 跨路径一致性` 的固定顺序执行；首次不得随机抽查。
  2. 每一步只记五态之一：
     - `✅ 符合`：实际结果与路径预期一致；
     - `❌ 不符合`：路径有明确预期，原型未实现或实现错误；
     - `🔍 事实源疑问`：PRD 缺失、冲突或需要业务取舍；
     - `⚠️ 原型限制`：外部副作用等静态原型明确不模拟；
     - `📌 已知不处理`：已有明确裁决和依据。
  3. 对 `❌/🔍` 立即分配 `W2-xxx`；负责人只需提供最小事实包：
     - `PATH-ID`；
     - 使用的角色/前置状态；
     - 做了什么；
     - 预期什么、实际发生什么；
     - 截图或可复现补充（如有）。
  4. 同一路径全部登记后再交 Agent 核查；走查中不即时改原型，避免后半程基线变化。
- **R｜结果**：所有人工发现均有路径锚点、复现条件和原始描述。
- **卡点 G5**：缺 `PATH-ID`、角色/前置、动作或实际现象的问题只可标“待补复现”，不得进入修复。

### S6｜Agent 核查、归因和裁定责任层

- **W｜触发时机**：收到一条完整问题，或负责人结束一条大路径的走查。
- **A｜行动**：
  1. 先复现，再依次查 `PRD-ID → PATH-ID → 原型定位`。
  2. 每条问题只选一个首要责任层：

     | 责任层 | 判据 | 下一步 |
     |---|---|---|
     | PRD | 需求缺失、冲突、边界不明或新业务取舍 | 标“待负责人裁决”，不改下游 |
     | 路径 | PRD 已明确，但路径漏写、误读或预期不完整 | 先修路径，再评估原型 |
     | 原型 | PRD 与路径一致，原型未实现或实现错误 | 可进入原型修复 |
     | 原型限制 | 外部副作用或本轮明确不模拟 | 记录依据，不伪造实现 |
     | 环境/操作 | 打开旧文件、状态未复位、角色或数据前置不满足 | 修正环境后原路径重走 |

  3. 若修改基础事实，先列出影响清单：PRD 哪些条目、哪些 PATH、原型哪些页面/状态、哪些已关闭问题需回归。
  4. 在问题账本补齐：PRD 依据、核查三态、责任层、根因、方案与代价、影响清单、状态。
- **R｜结果**：每条问题知道“错在哪一层、先改哪一份、谁来裁决”。
- **卡点 G6**：责任层未定、PRD 依据缺失或负责人裁决未完成，不得改原型。

### S7｜按瀑布顺序修复

- **W｜触发时机**：G6 通过；若责任层为 PRD，须负责人裁决完成后触发。
- **A｜行动**：
  1. 一次只处理一个业务路径或一组同根因问题，形成一个修复批次。
  2. 若 PRD 有变化：先改 PRD 原子条目与词表，再更新所有受影响 PATH。
  3. 若仅路径有变化：修改路径和覆盖索引，并检查是否改变原型预期。
  4. 原型只实现已经由 PRD 与路径共同确认的行为；不得写隐藏业务规则补洞。
  5. 更新问题账本中的“实际改动、代价、验证、回滚方法”；不覆盖负责人原始描述。
- **R｜结果**：每批修改都沿事实源向下传播，无反向定义需求。
- **卡点 G7**：上游已变、下游影响清单尚有未处理项时，本批不得交复验。

### S8｜机器检查与负责人复验

- **W｜触发时机**：每个修复批次完成后；三文档准备定稿前再全量触发一次。
- **A｜行动**：
  1. Agent 执行并登记真实输出：
     - PRD-ID、PATH-ID 唯一性；
     - 双向覆盖缺口；
     - 旧事实源、旧文件名、旧品牌、禁用术语和冲突数值残留；
     - HTML 可加载、内部导航可达、控制台错误；
     - 受影响页面的结构、语义控件和关键状态切换。
  2. 检查结果只用三态：`已验证`、`未验证`、`失败（附原始报错）`；文档结构检查不得写成“测试通过”。
  3. Agent 将问题状态更新为“已修改待复验”。
  4. 负责人必须从原 `PATH-ID` 的前置状态开始重走，不接受只看修改后页面截图。
  5. 负责人确认符合后，问题才标“已关闭”；不符合则更新原问题，不另建重复问题。
- **R｜结果**：机器验证结构和可执行性，负责人验证业务合理性，证据落在同一问题条目。
- **卡点 G8**：没有验证命令/路径与真实输出，或没有负责人原路径复验，不得关闭问题。

### S9｜三文档定稿与移交

- **W｜触发时机**：全量走查结束，最后一个修复批次完成复验后。
- **A｜行动**：按下列清单做一次全量终审，记录三份文档最终 SHA-256 和日期；版本统一标为 `vFinal` 或负责人确认的正式版本号。
- **R｜结果**：PRD、业务路径、统一原型成为可追溯、互相咬合的开发前输入；问题账本保留为过程证据。
- **卡点 G9**：定稿清单未全部满足，不进入六要素创建。

## 6. 定稿清单（G9）

### 6.1 PRD

- [ ] 每条有效需求有唯一 `PRD-ID`，可独立判断。
- [ ] 角色、状态、数值、术语和废止能力内部一致。
- [ ] 所有待定项有负责人、裁决时机和影响；不存在未标记空白。
- [ ] 技术验证项没有伪装成业务定论。
- [ ] 未包含页面布局、组件写法等实现细节。

### 6.2 业务路径

- [ ] 每个 `PATH-ID` 均引用有效 `PRD-ID`。
- [ ] 每个步骤均含前置、动作、预期、分支/例外、原型边界。
- [ ] PRD 中适用于路径验证的需求覆盖率为 100%。
- [ ] 非 UI 或原型不能模拟的需求逐条显式列出，没有静默跳过。

## 8. 变更与批次纪律

1. **发现批次**：负责人完成一条大路径后交付，不在走查途中改原型。
2. **裁定批次**：Agent 可集中核查，但每条问题保持独立责任层和证据链。
3. **修复批次**：按同一业务路径或同一根因聚合；不得把无关修改夹带进来。
4. **复验批次**：先定向复验受影响 PATH，再跑横切一致性；事实源变化时回归所有引用它的路径。
5. **回滚**：只撤销本批实际改动，不覆盖其他批次或负责人已有修改。
