## 一、开工前提

逐项确认，缺一项不开并行：

- [ ] 六件套已产出，**A 组卡点全绿**（B 组随任务逐个生效，不是前提）
- [ ] `tasks.yaml` 已按手册 2 的九字段 schema 拆分完毕并合入 `main`；两个任务是否冲突只看 `writeSet`，不看引用集。`REWORK_LOG.md` 的七列只追加新行是唯一保留例外，不进入 `writeSet`
- [ ] 各设备工具链版本一致（对照⑤附录·运行时事实逐台核对 Node / 包管理器 / 测试框架版本）
- [ ] 进度快照与先红留证的生成 / 读取命令已登记进⑤附录·运行时事实（补位实查与测试拍都要用）
- [ ] 各设备 `gh` CLI 已登录同一仓库（挂号、状态实查、收口都依赖它）
- [ ] 仓库已创建 `task`、`blocked`、`cancelled` 三个标签；主分支保护要求 PR、必需 CI，支持 merge queue 时已启用
- [ ] 全部设备使用⑤附录指定的同一种命令环境；下文命令按 POSIX / Git Bash 写，项目若用 PowerShell，等价命令必须先写进⑤附录再开工
- [ ] 仓库级配置已通过一条独立初始化 PR 合入且验证；**不得在每台设备重复追加**：

```text
.gitattributes  精确包含一行：REWORK_LOG.md merge=union
.gitignore      精确包含一行：.runtime/

验证：
git check-attr merge -- REWORK_LOG.md   # 输出：REWORK_LOG.md: merge: union
git check-ignore .runtime/probe         # 输出：.runtime/probe
```

- [ ] 每台设备只执行本地配置：`git config rerere.enabled true`。`rerere` 只复用候选解法，仍须人工看 diff 并重跑闸门

## 二、角色与红线

### 2.1 五个角色

```
负责人（你，唯一的人）
 │
 ├── 并行管理 session ×1（常驻你身边，全程不关）
 │      实查池子状态 → 每当有位空出，算出下一个该派谁 → 产出启动提示词
 │
 └── 每个已开工的任务，在自己的设备上开三个 session：
        ├── 任务管理 session   编排：产出分段提示词、读报告、定下一段
        ├── 执行 session       干活：挂号开 draft PR、跑预写测试、写代码、转正 PR → 报告落 .runtime/exec/
        └── 核查 session       核查：只看客观产物                     → 报告落 .runtime/review/
```

| 角色 | 做什么 | 不做什么 |
| :--- | :--- | :--- |
| **负责人**（你） | 搬运**提示词**与**文件路径**；只读实查代码与闸门；发布 PR 评论、发起协调 PR；**亲自合并**；主干验证后补位 | 不亲自写功能代码、不亲自核查、不改 session 的报告内容 |
| **并行管理 session** | 实查池子状态；维护就绪队列；每次补位算候选；产出启动提示词 | 不介入任务内部执行 |
| **任务管理 session** | 产出每段提示词并标明去向；读报告文件后判断、产出下一段 | 不自己写代码、不自己核查、不臆测结果 |
| **执行 session** | 按提示词执行；全程维护本任务唯一的 PR（挂号 → 转正）；回读 CI；**报告写入 `.runtime/exec/`** | 不合并 `main`、不改 `tasks.yaml` |
| **核查 session** | 按提示词逐项核对、**只写指定的 `.runtime/review/` 报告** | 不改任何受版本控制文件、不写其他文件、**不读 `.runtime/exec/`** |

### 2.2 报告文件约定

所有工作报告落在 worktree 内的 `.runtime/`，已 gitignore，**永不进入提交**：

| 目录 / 文件 | 谁写 | 谁能读 |
| :--- | :--- | :--- |
| `.runtime/exec/<任务id>-<两位序号>.md` | 执行 session | 你、任务管理 session |
| `.runtime/review/<任务id>-<两位序号>.md` | 核查 session | 你、任务管理 session |

序号按循环轮次递增：`T001-01.md`、`T001-02.md`……你回传时只需给任务管理 session 一句话加路径，它自己去读。每份报告首部必须写 `Task-ID`、角色、Commit SHA、执行时间；命令输出保留原文结构，但密钥、令牌、Cookie、个人信息必须替换为 `[REDACTED:<类型>]`，并注明发生了脱敏。

`.runtime/` 是工作副本，不是永久证据。最终核查结束或任务撤出时，负责人必须在删除 worktree 前把**脱敏后的最终执行报告与最终核查报告**分别归档为 PR 评论；已有 CI 日志只贴链接与 Commit SHA，不在评论重复大段输出。归档评论只追加、不编辑；订正另发新评论并引用旧评论。归档完成后才允许清理 worktree。

### 2.3 六条红线

1. **session 之间不能互相通信，你是唯一通道。**任务管理 session 只能读到你指给它的报告文件。
2. **报告保留原始证据，但安全优先。**命令输出、报错、CI 状态保留原文结构，不写"已完成""运行正常"这类概括；密钥、令牌、Cookie、个人信息必须脱敏并留下 `[REDACTED:<类型>]` 标记。
3. **核查 session 禁止读取 `.runtime/exec/`。**报告落盘之后，双盲不再由"你没粘贴"来保证，只能靠这条禁令——它必须写进每一段核查提示词。
4. **给核查 session 的信息只有客观产物**：PR 链接、Commit SHA、`git diff`、CI 状态、`REWORK_LOG` 新增行；不提供执行报告。
5. **Agent 永不合并 `main`**——职责止于建与转正 PR、回读 CI、写报告。
6. **功能分支永不修改 `tasks.yaml`。**改任务清单一律走独立协调 PR，A 组全绿后由负责人合入 `main`；是否需要暂停补位、要不要重发启动提示词，按改动性质判定——**判定表见 §4.6，不在此重复**。

## 三、调度模型

**滚动补位，不分批。**维持一个在跑池；任一任务合并且主干 CI / 进度快照确认“已完成”后才腾位，立刻从就绪队列补进下一个。**不等其他任务，但也不拿 merged 状态冒充完成。**

| 概念 | 是什么 |
| :--- | :--- |
| **在跑池** | 带 `task` 标签、PR 正文含 `Task-ID: Txxx`、处于 open 状态且**没有** `blocked` 标签的任务 PR。容量 = WIP 上限 |
| **阻塞保留区** | 带 `task` + `blocked` 标签的 open draft PR；不占 WIP，但保留任务、PR 号、分支和诊断证据，不能被再次派发 |
| **合并未确认区** | PR 已 merged，但进度快照尚未把该 Task-ID 推导为已完成（收口 F6 进行中）。`writeSet` 仍视作占用，任务本身不可再派发；F6 失败转恢复 PR，成功后随快照更新自然移出 |
| **WIP 上限** | 由你的搬运带宽决定，**起步 2–3**。worktree 彼此隔离，一台设备可承载多个任务，设备数不构成硬上限 |
| **就绪队列** | 同时满足四条：<br>① CI 生成的进度快照中 `dependsOn` 全部为**已完成**<br>② 自身不在已完成、在跑池、合并未确认区或阻塞保留区<br>③ 与在跑池及合并未确认区每个任务的 `writeSet` 无文件相等、目录包含或交叉<br>④ 九个字段及锚点校验仍为 A 组全绿。按关键路径优先排序 |

判据③比的是**当前在跑池与合并未确认区**，不是"同一批"——池子滚动，任务生命周期会交错重叠，按批比会漏判冲突。合并未确认区必须纳入②③：merged 而主干未确认的任务若被提前视作释放，F6 一旦失败开恢复 PR，就会与窗口期内新派的任务撞写集，或被当作从未开工的任务重复派发。`ruleRefs`、`operationRefs`、`specRefs`、`acceptanceTests` 是读取 / 验收引用，允许重叠；只有 `writeSet` 决定并行冲突。若任务确需改测试文件或生成快照，该路径也必须在 `writeSet` 中，因此无需另设“一任务一测试文件”惯例。唯一例外是 `REWORK_LOG.md` 的七列只追加新行：由 `merge=union` 与 append-only 卡点保护，不参与写集冲突；改删旧行仍按越界处理。

**排序**：关键路径优先（位于最长 `dependsOn` 链上的优先）；同链长时，**直接解锁下游任务多者优先**——它合并后就绪队列回血最快，池子不容易断粮。

**池子状态从证据推导，不靠记忆。**挂号机制（§4.3 第一拍）保证每个任务从第一段起就有带 `Task-ID` 和 `task` 标签的 draft PR：open 且无 `blocked` = 在跑，open 且有 `blocked` = 阻塞保留。**merged 只证明代码已合并，不等于任务已完成**；完成状态只能读取 CI 生成的进度快照，它还要求主干 A 组与该任务适用 B 组全绿。merged 而快照未确认 = 合并未确认区，`writeSet` 按占用计算。并行管理 session 每次补位自己实查 PR 与进度快照；任一来源不可用就停止派新任务，不接受口头状态替代。session 丢失上下文时，重开并重喂 §6.1 即可恢复。

**WIP 调节**：瓶颈通常是你，不是设备。设备常在等你搬运 → 降 1；设备常空闲而就绪队列有货 → 升 1。一次只调一档。

## 四、流程

全流程一张图（编号对应后续小节）：

```
                ┌──── F6 主干验证通过后腾位补位（等待期间可预算下一位，见 F6/F9）────┐
                ▼                                                                  │
就绪队列 ──§4.2 补位──▶ §4.3 执行循环                                               │
                        挂号→契约→测试→实现→闸门→转正→核查                          │
                          │                 │              │                       │
                          │ 契约缺口 /       │ 核查不通过     │ 核查通过              │
                          │ 返工止损         ▼              ▼                       │
                          ▼           §4.4 返工循环    §4.5 收口：亲自合并 ──────────┘
                    §4.4 阻塞保留      R1–R5 修完复审
                    登记缺口回规格循环   通过→收口
                    释放设备但保留 PR    仍不通过→再返工
```

### 4.1 初始化（全程只做一次）

| # | 动作 |
| :- | :--- |
| **I1** | 定 WIP 上限 N |
| **I2** | 各设备主工作区同步基线：`git fetch origin && git switch main && git pull --ff-only`，逐台核对 `git rev-parse HEAD` 与 `git rev-parse origin/main` 一致 |
| **I3** | 开**并行管理 session**（全程不关），喂 §6.1 提示词 |
| **I4** | 连续走 N 次 §4.2 补位，把在跑池填满 |

### 4.2 补位（初始化时，或任一任务合并后）

| # | 动作 |
| :- | :--- |
| **P1** | 回到并行管理 session，只报一句：<br>`空闲设备：A，请给下一个。`<br>它自己 `git fetch origin`，查询带 `task` / `blocked` 标签的 open PR，并读取 CI 生成的进度快照。任一实查失败：输出原始报错并停止派工，不接受口头状态替代 |
| **P2** | 它按第三章四条判据算出就绪队列，给出**队首任务 + 该任务的启动提示词**（§6.2 模板）。启动提示词必须携带九字段及 `tasks.yaml` 所在 Commit SHA。若队列为空，走 §4.6 |
| **P3** | 到空闲设备上 `git fetch origin`（worktree 直接从 `origin/main` 建，不需要动本地分支） |
| **P4** | 建 worktree、分支、报告目录：<br>`git worktree add ../wt-T004 -b feature/T004-<slug> origin/main`<br>`mkdir -p ../wt-T004/.runtime/exec ../wt-T004/.runtime/review` |
| **P5** | 开三个 session：`T004-管理` / `T004-执行` / `T004-核查`，把启动提示词粘进管理 session。它产出的第一段必然是「挂号」，进入 §4.3 |

### 4.3 执行循环（每设备各自转，互不等待）

你搬运的只有提示词和一行路径：

```
[你] 把启动提示词喂给「任务管理 session」
        │
        ▼
   任务管理 session 输出：标注（去向 / 本段目标 / 报告写到哪个文件）
                        + 一个独立代码块（纯提示词，可整块复制）
        │
        ▼
[你] 整块复制 → 粘到「执行 session」或「核查 session」→ 运行
        │
        ▼
   该 session 干完活，把报告写进指定的 .runtime/ 文件
        │
        ▼
[你] 回到「任务管理 session」，只说一句：
     "已完成，报告在 .runtime/exec/T004-03.md"
        │
        ▼
   任务管理 session 自己读该文件，三选一输出：
     · 下一段提示词（含标注 + 代码块）
     · "沿用上一段，无需更新" + 原因
     · "本阶段完成，进入下一步" / "本任务完成"
        │
        └──► 回到第 2 步，直到节拍走完、PR 已转正、核查通过
```

**七拍顺序由任务管理 session 把关**（其中契约→测试→实现→闸门即手册 2 的固定四步）：

| 拍 | 谁跑 | 达标标志 |
| :- | :--- | :--- |
| **挂号** | 执行 session | 空提交的 message trailer 含 `Task-ID: T004` 并已 push；draft PR 标题为 `T004: <title>`、正文含 `Task-ID` / 九字段来源 Commit SHA、带 `task` 标签；PR 号与 HEAD SHA 已写进报告。B 组自此可按 Task-ID 激活，ADR 编号自此可用 |
| **契约** | 执行 session | 九字段全部与指定 Commit 的 `tasks.yaml` 一致；②类型及适用的 `ruleRefs`、`operationRefs`、`specRefs` 均可解析，L1 的规则 / 接口数组为 `[]`；计划改动未越出 `writeSet`。缺任何一项：进入 §4.4 阻塞保留，不在功能分支补规格 |
| **测试** | 执行 session | 在实现 diff 产生前，按当前 `Task-ID` 首次执行**已经存在**的 `acceptanceTests`，由独立 CI / workflow 留下目标能力先红的 Commit SHA 和原始输出；先红留证只跑本任务 `acceptanceTests`，不要求全量闸门；不得先写实现再补测试 |
| **实现** | 执行 session | 测试变绿，且未修改测试迁就代码 |
| **闸门** | 执行 session | 先同步主干：`git fetch origin && git rebase origin/main`（冲突按第五章解）后 `git push --force-with-lease`；A 组 + 当前 `Task-ID` 适用 B 组在 rebase 后 HEAD 全绿；CI 明列启用 / 跳过项及理由，HEAD SHA 与报告一致。此后核查绑定的即是近线 SHA，收口 F2 通常只剩快路径 |
| **转正** | 执行 session | PR 标记 ready for review；描述补全：改动清单、命令与真实输出、剩余风险 |
| **核查** | 核查 session | 逐项核对通过（清单见 §6.3）。不通过走 §4.4 |

**一个任务在首次合并前只有一个 PR：挂号时开，收口时合。**返工与阻塞恢复都在原分支、原 PR 继续，不关不重开——PR 号从头到尾唯一，ADR 编号也不会因返工而变。唯一例外是合并后主干 CI 失败：原 PR 已不可追加，此时才以同一 `Task-ID` 新开恢复 PR。

**循环全程随时可能触发的两个动作**，任务管理 session 应在对应时机写进提示词：

- **需要新 ADR 时**：先确认 ADR 路径及其技术栈快照出口已在本任务 `writeSet`；若不在，先按 §4.6 阻塞并通过协调 PR 扩边界。边界具备后直接命名 `adr/ADR-<PR号>-<该PR内序号>-<slug>.md`——挂号先行，PR 号从第一拍就有，不再使用 `draft-` 过渡。**序号从 1 起，本 PR 只有一条 ADR 时也写 1**；正文固定五段：状态、背景、决策、后果、边界。不改已合入的 ADR 编号
- **出错的当下记账**：`REWORK_LOG.md` 追加一行，七列填全：日期、现象、主归因、逃逸原因、涉及交付物、处置、同类第几次。**修正既有条目时新开一行并引用旧行日期，不在原行续写**

### 4.4 核查、返工与阻塞保留

结论只有**通过 / 不通过**两态，没有"有条件通过"。

**本任务边界内发现任何问题即判不通过，一律返工修完，不留遗留**——问题不分大小。留下的小问题没有任何机制保证它会被处理，等下次看到时它已经变成"一直都这样"。

唯一的例外是**越界发现**：核查顺眼看到的、其修复需要越出 `writeSet`，或不属于本任务 `pathSegment` / `ruleRefs` / `operationRefs` / `specRefs` 的问题。这类**本任务无权修**——改了就超出范围，反而会被核查清单第一条判不通过。

| 发现位置 | 影响结论吗 | 处置 |
| :--- | :--- | :--- |
| **本任务边界内** | 是，判不通过 | 走 R1–R5 返工修完，一个不留 |
| **本任务边界外** | 否 | 核查报告中单列成节。**核查通过后、进入收口前，由你把该节原文贴为 PR 评论**（`gh pr comment`）——PR 是永久载体，裁决（F7）从此不受 worktree 清理时限约束。裁决结果二选一：补进 `tasks.yaml` 成为新任务，或判为非问题并在评论下留一句结论。**不得在本任务内顺手修** |

补进 `tasks.yaml` 属于**纯新增**，按 §4.6 走独立协调 PR，不需要暂停已有在跑任务；新任务只有在协调 PR 合入且 A 组全绿后才进入下次就绪队列计算。

**判不通过后的返工循环**：

| # | 动作 |
| :- | :--- |
| **R1** | 任务管理 session 读核查报告，**逐条**产出返工提示词，每条标明回到七拍中的哪一拍 |
| **R2** | 执行 session **只修登记的问题，不得顺带扩大范围**。顺手改的东西核查看不见，等于绕过闸门 |
| **R3** | 修完**重跑该拍及其之后所有拍的卡点**，不是只跑失败那一项；push 到**原分支原 PR**，不新开 PR |
| **R4** | 记账：本次问题按七列追加进 `REWORK_LOG.md`；主归因四选一，另填逃逸原因。核查发现不等于框架漏洞——普通实现偏差仍归 Agent 幻觉，缺失闸门写进逃逸原因。同类 Agent 执行偏差第二次才固化⑤；确认是框架漏洞则首次修机制 / 卡点。固化文件不在 `writeSet` 时先走协调 PR扩边界 |
| **R5** | 优先交**原核查 session** 复审。若原 session 丢失或不可用，新开核查 session 并执行 §6.3 **全量核查**，不得只看旧问题清单。复审报告绑定当前 Commit SHA |

复审通过 → 走 §4.5 收口；仍不通过 → 回 R1。

**返工止损：同一任务返工超过 2 轮仍不通过，暂停继续修改，先按四分类重新诊断。**不得自动判成业务理解偏差：Agent 幻觉可更换执行 session 后继续原 PR；框架漏洞先走协调 PR 修闸门；业务理解偏差回规格循环；外部环境失败等待环境恢复或定义降级。需要等待上游 / 外部变化的任务进入下述阻塞保留流程，设备立即走 §4.2 补位。

**阻塞保留流程**（返工止损，或契约拍停工）：

| # | 动作 |
| :- | :--- |
| **B1** | 任务管理 session 输出诊断：主归因、逃逸原因、缺失的权威源、解除条件；执行 session push 当前可保留内容，PR 转回 draft |
| **B2** | 给原 PR 加 `blocked` 标签，正文写 `Block-Reason: spec / framework / environment`；PR 保持 open，因此不会被再次派发，且不占 WIP |
| **B3** | 七列追加 `REWORK_LOG.md`，把脱敏后的最终执行 / 核查报告归档为该 PR 评论；确认远端已有全部需保留提交 |
| **B4** | 关三个 session；用 `git worktree list` 核对目标路径后清理本地 worktree。分支、PR 号和 ADR 编号保留 |
| **B5** | 上游修复走独立协调 PR。合入且 A 组全绿后，从原分支重建 worktree、rebase `origin/main`、移除 `blocked`、按最新 `tasks.yaml` Commit 重新下发启动提示词，继续**原 PR** |

只有任务被明确取消时才关闭 PR：先通过协调 PR 删除 / 取代 `tasks.yaml` 条目并归档证据，再给 PR 加 `cancelled` 标签后关闭；PR 号和其中 ADR 编号永不复用。

### 4.5 单任务收口（跑完就收，不等其他任务）

| # | 动作 |
| :- | :--- |
| **F1** | **只读实查**：`gh pr view <n> --json title,body,labels,headRefOid,statusCheckRollup`；确认 `Task-ID`、`task` 标签、九字段来源 Commit、当前 HEAD SHA；除 `REWORK_LOG.md` 七列只追加新行外，diff 全在 `writeSet`，且不含 `.runtime/` |
| **F2** | 让执行 session `git fetch origin`：若 `origin/main` 自闸门拍后未移动，直接进 F3（快路径）；移动了则 `git rebase origin/main`，按第五章解冲突并检查 diff，然后执行 `git push --force-with-lease`。若 lease 失败，停止并实查远端新增提交，禁止改用裸 `--force` |
| **F3** | 以当前远端 `headRefOid` 为唯一候选 SHA，重跑 A 组与适用 B 组并等待全绿。核查结论沿用规则：rebase 无冲突、且 `git diff origin/main...HEAD` 与被核查版本一致（可用 `git range-diff` 核对）→ 沿用原核查结论，在 PR 评论记录新旧 SHA；发生冲突解决或 diff 有实质差异 → 交原核查 session 对候选 SHA 重新核查，其中冲突解决必须全量核查 |
| **F4** | 把脱敏后的最终执行报告、绑定候选 SHA 的最终核查报告分别归档为 PR 评论；越界发现也已单列为 PR 评论。确认评论或 CI 链接可读后再继续 |
| **F5** | **负责人亲自合并**。合并前再次确认 PR HEAD 仍等于 F3 / F4 的候选 SHA；仓库支持 merge queue 或“分支必须最新”保护时必须启用 |
| **F6** | **合并后回读**：等待 `main` 侧 CI 全绿、进度快照把该 Task-ID 推导为已完成、技术栈快照已刷新。任一失败都不腾 WIP、不解锁下游；立即以同一 Task-ID 开恢复 PR 修复或回滚。等待期间可回并行管理 session 按「本任务已完成」假设预算下一位（只做 P1–P2，产出启动提示词备用，不建 worktree）；F6 失败即废弃预算结果 |
| **F7** | **裁决越界发现**：判为非问题 → 评论下留结论；要立项 → 发独立协调 PR 追加九字段任务，A 组全绿后合入。纯新增不暂停已有在跑任务 |
| **F8** | **关三个 session，清理 worktree**：先确认 F4 已归档，再用 `git worktree list` 核对解析后的目标路径确为本任务 worktree，最后执行 `git worktree remove --force ../wt-T004` |
| **F9** | **立即补位**：仅在 F6 已完成后实际派发——F6 期间已预算的，直接从 P3 建 worktree 开工；未预算的回 §4.2 从 P1 走起 |

无需"定合并次序"——`dependsOn` 未完成的任务根本进不了就绪队列，拓扑序自动成立，谁先好谁先合。

### 4.6 卡住与复盘

**就绪队列空了**，按顺序试：

1. **先把在跑池里最接近完成的任务推到主干验证完成**——完成会解锁下游，也会释放它占用的 `writeSet`，队列多半立刻就有货
2. 仍为空 → 该设备**暂时闲置**，不要硬派冲突任务进池
3. **反复出现队列空** → 任务图太窄（层宽不足），回手册 2 §1.2 重拆任务边界

**阶段性复盘**（每合完 5–10 个任务，或队列空闲时）：

- 同一对任务反复冲突 → 在 `tasks.yaml` 中重拆这两个任务的边界
- 实测耗时分布极度分散 → 边界粒度不均，同样回手册 2 §1.2
- 就绪队列常因目录级 `writeSet` 条目互斥而排空 → 回手册 2 §1.3 把 `writeSet` 从目录细化到文件，缩小冲突面

**改 `tasks.yaml` 的判定表**（红线 6 所指，全 SOP 唯一一份）：一律走独立协调 PR，A 组全绿后由负责人合入，是否暂停派工看改动性质——

| 改动性质 | 暂停补位吗 | 额外动作 |
| :--- | :--- | :--- |
| 纯新增任务（如收口 F7 的越界发现立项） | 否 | 合入后重算队列；新任务此前不可派发 |
| 改未开工任务的字段 / 删未开工任务 | 否 | 合入后重算队列，并使用新的 `tasks.yaml` Commit SHA |
| **改在跑 / 阻塞任务的任一字段** | **是** | 先给相关 PR 加 `blocked` → 暂停新派工 → 协调 PR 合入 → 重算所有在跑任务的 `writeSet` 冲突 → 给受影响任务重发九字段启动提示词 → 移除可恢复任务的 `blocked` |
| **删除在跑 / 阻塞任务** | **是** | 协调 PR 合入后执行取消协议：归档报告、PR 加 `cancelled` 并关闭、清理 worktree，再恢复派工 |

**session / 设备失效恢复**：

- 并行管理 session 丢失：重开，喂 §6.1；它从 PR 标签、Task-ID 和进度快照重建状态
- 任务管理 session 丢失：重开，喂 §6.2 已填充提示词、当前 PR 链接和已有报告路径；先读证据再决定所处节拍
- 执行 session 丢失或设备离线：在另一设备从远端原分支重建 worktree；未 push 的改动一律视为不存在，不靠口头复原
- 核查 session 丢失：新开后执行 §6.3 全量核查；不得把旧 session 的局部问题清单当作完整核查
- 任一恢复都追加 `REWORK_LOG.md`；设备 / 网络故障主归因为外部环境失败，是否存在流程逃逸另填「逃逸原因」

## 五、冲突处置速查

| 冲突在哪 | 怎么做 |
| :--- | :--- |
| `tasks.yaml` | 不该发生（功能分支禁改）。确认分支侧没有合法任务变更后，用 `git restore --source=origin/main --staged --worktree -- tasks.yaml` 精确恢复；需要的任务变更另走协调 PR。禁止依赖 rebase 下易混淆的 ours / theirs |
| `REWORK_LOG.md` | `merge=union` 只负责保留新增行；合并后逐行检查七列、去掉完全重复行。仍冲突说明有人行内续写——拆成两条只追加记录分别保留 |
| `adr/` 编号重复 | 用 `PR号-序号` 后本不该发生（PR 号仓库内唯一且不复用）。若出现，说明有人手写了编号：改回真实的 `PR号-序号`，重跑唯一性卡点 |
| `AGENTS.md` ADR 索引段 / `README` 快照块 | **只重建标记块**，禁止 checkout 整个文件。`AGENTS.md` 的规则正文是源，先确认其 diff 未丢失，再从 `adr/` 运行生成脚本覆盖索引块；README 同理 |
| `AGENTS.md` 规则正文 | 语义化解冲突：兼容且都有效才保留；互相矛盾时按权威源和返工归因裁决，禁止“两个都留”。同时守住单文件 20 条上限 |
| ①②③④或⑥源文件 | 按 `writeSet` 本不应冲突。发生即停止 rebase，检查是否越界或 `tasks.yaml` 写集错误；修任务边界后再继续，不能现场猜着合 |
| `package.json` / lockfile | 引新依赖的任务 `writeSet` 必含这两个文件，调度上天然互斥，不该并行相撞。若仍冲突：`package.json` 语义化手解（保留双方依赖项），lockfile 一律不手改——删除冲突文件后用⑤附录指定的包管理器重新生成，再重跑闸门。频繁互斥 → 把依赖引入抽成星形前置任务（手册 2 §1.2） |
| 截图基线 | 先取最新主干基线，再只对当前任务 `acceptanceTests` 覆盖的截图执行 `--update-snapshots`；核对实际变更文件都在 `writeSet`，PR 描述说明视觉意图。禁止无范围地更新全部基线 |
| `.runtime/` 被跟踪或出现在冲突里 | 立即停止收口；先归档脱敏报告，再通过协调 PR 修 `.gitignore` / 索引。执行取消跟踪前用 `git ls-files .runtime` 列出精确目标，禁止对未核对路径做递归清理 |

三条通则：

- 冲突解完**必须 push `--force-with-lease`，对新 SHA 重跑闸门并重新核查**，不得解完直接合。
- **不回改已合入的 ADR 编号，也不因并行合入顺序给后合者重新编号**；PR 号已经保证唯一。
- **派生标记块一律从源重新生成**；含源内容的混合文件只覆盖标记块，不替换整文件。

滚动补位下 rebase 触发得频繁，但每次量小——一次只合一个任务，冲突面天然有限；`rerere` 会自动复用你解过的冲突。

## 六、提示词

以下每个代码块都可整块复制。

### 6.1 并行管理 session 启动提示词

**用时**：全程只开一次（I3），此后每次补位都回到这个 session 追问。

```text
你是本项目的并行管理 session，全程常驻。先读 AGENTS.md、tasks.yaml、手册 2 §1.3 与当前进度快照。
你不执行任何任务，只做三件事：实查池子状态、维护就绪队列、产出启动提示词。

调度方式是滚动补位，不分批：在跑池容量为 <N>；任务只有在合并后主干 CI 全绿、进度快照显示已完成，才释放 WIP 并解锁下游。

【每次我来补位时，我只告诉你】
  空闲设备：<设备名>

【你要做的】
第零步 · 实查状态，不接受申报：
  git fetch origin
  gh pr list --state open --label task --limit 1000 \
    --json number,title,body,labels,headRefOid,url
    → 正文含 Task-ID、无 blocked 标签 = 在跑池
    → 正文含 Task-ID、有 blocked 标签 = 阻塞保留区
  gh pr list --state merged --label task --limit 30 --json number,title,body,mergedAt
    → 正文含 Task-ID 且进度快照未标已完成 = 合并未确认区（writeSet 仍占用，任务不可再派发）
  运行⑤附录登记的进度快照生成 / 读取命令 → 唯一的已完成与依赖状态来源
  任一实查失败：贴原始报错并停止派工，不接受我口头申报状态。

第一步 · 算就绪队列。一个任务就绪，须同时满足：
1. 进度快照中 dependsOn 全部为已完成
2. 自身不在已完成、在跑池、合并未确认区或阻塞保留区
3. 与【在跑池及合并未确认区每一个任务】的 writeSet 无文件相等、目录包含或交叉
4. tasks.yaml 九字段及其锚点的 A 组校验全绿
ruleRefs、operationRefs、specRefs、acceptanceTests 是引用集，允许重叠；只有 writeSet 判并行冲突。
排序：关键路径优先（位于最长 dependsOn 链上的优先）；
同链长时，直接解锁下游任务多者优先。

第二步 · 输出：
- 队首任务 id 与标题
- 该任务的启动提示词：严格套用 SOP §6.2 模板，只替换 <> 占位符，其余一字不改；
  九字段必须逐字取自同一版本 tasks.yaml，并填入该文件所在 Commit SHA；
  放在一个独立代码块里，块内不含任何解释文字
- 队列中其余候选（仅列 id，供我预判）
- 若队列为空：说明每个未开工任务分别被什么阻塞
  （依赖未完成 / 已在跑 / 合并未确认 / blocked / writeSet 与哪个在跑或合并未确认任务冲突 / A 组失败），
  并指出在跑池中哪个任务完成后能解锁最多下游

不要估工时，不要给日期。
```

### 6.2 任务管理 session 启动提示词（模板）

**用时**：由 §6.1 按任务填充后交给你；带到该任务的设备，粘进 `<id>-管理` session。

```text
你是任务 <id> 的任务管理 session。你不写代码、不做核查，只做编排。

任务档案（逐字摘自同一版本 tasks.yaml，不得改动）：
  tasksCommit:     <tasks.yaml 所在 Commit SHA>
  id:              <id>
  title:           <title>
  dependsOn:       <dependsOn>
  pathSegment:     <pathSegment>
  ruleRefs:        <ruleRefs>
  operationRefs:   <operationRefs>
  specRefs:        <specRefs>
  acceptanceTests: <acceptanceTests>
  writeSet:        <writeSet>
分支：feature/<id>-<slug>（worktree 已建，尚未 push）
边界：除 REWORK_LOG.md 七列只追加新行外，实际 diff 只能落在 writeSet；行为只覆盖 pathSegment 及其 ruleRefs / operationRefs / specRefs

【工作方式】
- 我（负责人）是唯一通道。你与执行 session、核查 session 不能直接通信。
  你能读到的只有我指给你的报告文件。不要臆测执行结果，没有报告就是没发生。
- 每次只输出一段提示词，格式固定为「标注在外、提示词在代码块内」：
    【去向】执行 session / 核查 session
    【本段目标】这一段要达成什么
    【报告写到】.runtime/exec/<id>-<两位序号>.md 或 .runtime/review/<id>-<两位序号>.md
    ```
    （纯提示词，块内不含任何解释文字，我要能整块复制直接粘贴）
    ```
  序号按轮次递增，从 01 开始。每份报告首部写 Task-ID、角色、Commit SHA、执行时间；
  原始输出中的密钥、令牌、Cookie、个人信息必须替换为 [REDACTED:<类型>] 并注明脱敏。
- 我回来只会说一句"报告已落盘：<路径>"。你自己去读那个文件再判断。
- 判断后三选一输出：
    · 下一段提示词（含上述标注 + 代码块）
    · "沿用上一段，无需更新" + 原因
    · "本阶段完成，进入 <下一步>" 或 "本任务完成"
- 判断只依据报告文件里的原文证据。证据不足时，直接要求我让对应 session 补取，不要放行。

【必须推过的七拍，顺序不可交换】
挂号 → 契约 → 测试 → 实现 → 闸门 → 转正 → 核查。
  挂号：第一段提示词。让执行 session 用空提交 push 分支：
        git commit --allow-empty -m "<id>: start" -m "Task-ID: <id>"
        开 draft PR，标题为 <id>: <title>，正文写 Task-ID: <id>、tasksCommit，添加 task 标签；
        把 PR 号和远端 HEAD SHA 写进报告。后续 B 组激活、ADR 编号、状态推导都用这些标识。
  契约：逐项核对九字段与 tasksCommit 对应文件一致；②类型及适用的 ruleRefs、
        operationRefs、specRefs 均可解析，L1 的规则 / 接口数组为 []；计划改动不越出 writeSet。
        缺任何一项：进入 SOP §4.4 阻塞保留，不在功能分支补规格。
  测试：acceptanceTests 在开工前已经存在。实现 diff 产生前，以当前 Task-ID 首次执行，
        由独立 CI / workflow 留下目标能力先红的 Commit SHA 与原始输出；先红留证只跑
        本任务 acceptanceTests，不要求全量闸门；不得先实现再补测试。
  实现：让测试变绿，不得修改测试来迁就代码。
  闸门：先让执行 session 同步主干：git fetch origin && git rebase origin/main，
        冲突按 SOP 第五章处理后 git push --force-with-lease；
        A 组 + 当前 Task-ID 适用 B 组在 rebase 后 HEAD 全绿；CI 明列启用 / 跳过项及理由。
  转正：让执行 session 把 PR 标记 ready for review，并补全描述：
        改动清单、命令与真实输出、剩余风险。
  核查：产出核查提示词交我带去核查 session。

【核查不通过时的返工循环】
核查结论只有通过 / 不通过两态。
本任务边界（writeSet + pathSegment / ruleRefs / operationRefs / specRefs）内发现任何问题即判不通过，一律返工修完，
不分大小、不留遗留。
唯一例外是越界发现——不在本任务边界内的问题，本任务无权修（改了就超范围）：
不影响本任务结论，让核查在报告中单列成节，由我贴 PR 评论后裁决，你不要安排修它。
判不通过后按下列顺序处理：
1. 逐条产出返工提示词，每条标明回到七拍中的哪一拍
2. 返工提示词里必须写明：只修登记的问题，不得顺带扩大范围
```
